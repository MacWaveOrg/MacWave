## 十一、`set -e` 撞上 `[[ 条件 ]] && 命令`：空依赖树让安装失败

**现象**：Format Test 的每一个测试包都报 `FAIL: install test_bin_*`，但同一段日志里
明明写着 `Successfully installed`、`Binary installed to …`、`Link created at …`。
紧接着 Random Test 也有零星几个包出现 `exit=0 <- 实际 1`，并且都伴随
「不带版本号的链接不存在」。

**根因**：路径重写脚本在建立「库文件名 → 实际路径」的兜底索引时，这样遍历依赖树：

```
for tree in "$BASE_DIR"/deps/*/*; do
    [[ -d "$tree" ]] && index_tree "$tree" "$MAP_FILE"
done
```

一个依赖都没装的时候，通配符不展开，`[[ -d ]]` 为假，于是 `&&` 这条命令整体返回 1。
脚本开头有 `set -e`，**立刻中止**。

关键在于中止的时机：包本体已经解压完、带版本号的链接也建好了，所以前面那些成功日志
全是真的；失败发生在最后的重定位阶段，而「建不带版本号的链接」排在它之后，因此永远
执行不到。用户看到的是一句毫无信息量的 `FAIL`。

Format Test 的测试包恰好都没有依赖，于是**每一个**都踩中。Random Test 只影响
「第一个带依赖的包装好之前」被抽到的那几个包 —— 于是表现成随机、偶发，很容易被当成
flaky 忽略掉。

**引入**：`01a0a71`（*Make Mach-O relocation orders of magnitude faster*）。提速本身
是对的，错在把循环体写成了 `[[ ]] && 命令` 这种「条件为假就返回非零」的形式。

**修复**：`6a87b86`，四处都改成显式 `if … then … fi`。空依赖树变成真正的空操作。

**教训**：`set -e` 的语义是「任何一条命令返回非零就退出」，而 `[[ ]] && cmd` 在条件
为假时**整体返回 1**。这种写法放在循环体或函数体里，正常分支也会变成致命错误。
要么写 `if`，要么在末尾补 `|| true` —— 前者更清楚，也更容易被下一个人看懂。

**排查提示**：日志里出现「成功」与「退出码非零」并存时，**信退出码**。它说明失败发生
在那句成功日志之后，去这一步的后续动作里找，不要回头怀疑已经成功的部分。

## 十二、限速校验用单次采样差值，把 token bucket 的突发放大成「超速」

**现象**：Random Test 偶发一条失败：

```
FAIL  --limit-rate 400K: 瞬时未超速（峰值 873K/s，容差 x2.0）  <- 峰值 873K/s > 800K/s
PASS  --limit-rate 400K: 全程平均未超速（2.1MB / 9.1s = 231K/s）
```

同一次运行里，「全程平均」是过的。平均 231K/s、上限 400K —— 限速显然生效了。

**根因**：瞬时速率取的是相邻两个 0.2 秒采样点的差值。限速器是 token bucket，允许成批
放行；一次 8KB 的突发恰好落在同一个 0.2 秒区间里，就会被算成数百 K/s 的尖峰。那既不是
持续超速，也不影响用户体感，但断言会失败。

**修复**：`4b9ef56`，改成「至少 1 秒滑动窗口内的平均速率」再取最大。

**验证方式值得记下来**：不是「跑一遍看看绿没绿」，而是

1. 用失败现场的数据（某 0.2 秒区间冲了约 175KB）复算：旧算法 875K/s（失败）、
   新算法 479K/s（通过）；
2. 再构造一个**真实**的持续 1MB/s 下载：新算法读到 1024K/s，仍然会失败。

第二条比第一条重要 —— 它证明放宽的只是噪声，不是判定本身。

**教训**：给「速率」下断言之前，必须先定义测量窗口。采样间隔天然抖动，单点差值测的是
瞬时吞吐，不是限速器的行为。另外，**修 flaky 必须同时给出反例**，否则只是在把测试改绿。

## 十三、索引里的记录指向了已被删除的文件

**现象**：

```
wave install test_no_sha256
🌊 Error: ErrorCode 404 - The URL or file does not exist.
🌊 URL: https://raw.githubusercontent.com/MacWaveOrg/MacWave/main/test_no_sha256
```

**背景**：这两个包是**故意做坏的负向测试样本** —— 一个记录里没有 `sha256`（验证
「跳过校验并给出警告」），一个 `sha256` 全是 `a`（验证「校验失败并删除损坏文件」）。
它们本身没有实际用途，存在的意义就是让安装器的两条错误分支有东西可测。

**根因**：载荷文件原本放在仓库根目录，`04564a1`（*Fix: completely replace main with
2.1.0*）重写主干时把它们删了，但索引记录没跟着改。

更麻烦的是两个架构还不一致：arm64 指向根目录，amd64 指向 `test/` —— 而 `test/`
这个目录**从来没存在过**。也就是说，两条记录里至少有一条在任何时刻都是错的。

**修复**：`d5350d6` 把两个文件恢复到 `test/`（那个 amd64 记录本来就期望的位置），
索引侧 `030a8aa` 把四个记录统一指向新路径。

**教训**：数据仓库和代码仓库是**两个独立的生命周期**。删掉代码仓库里的文件时，没有任何
机制会提醒你索引还在引用它。凡是索引里出现的 URL，都应当能在对应分支上取到；负向测试
样本尤其容易漏，因为它们平时根本不会被安装，404 可以潜伏一个多月没人发现。

校验器现在能检查 URL 是不是 HTTPS，但**不会联网确认它是否 200**。需要时得用审计脚本的
`--check-urls`（默认关闭，因为要联网）。

## 十四、分支保护一上，`GITHUB_TOKEN` 的镜像工作流立刻失效

**现象**：给所有分支加上「必须经 PR」的规则集之后，`sync-release-branch` 的推送会被拒绝。

**根因**：`GITHUB_TOKEN` 代表的是 GitHub Actions 机器人。规则集的 bypass 名单只接受
**组织管理员、团队、部署密钥、已安装的 GitHub App** —— 机器人身份不在其中。

这一点无法通过给工作流加 `permissions: contents: write` 绕开：那个只影响 token 能做什么，
不影响规则集对「谁可以豁免」的判断。

**修复**：镜像工作流改用 PAT，其属主是组织管理员，天然在 bypass 名单里。

顺带一个必须写进注释的细节：PAT 触发的 push 会**再次触发**同一个工作流。第二次运行会
发现两侧已经相等而直接退出，所以不会形成循环 —— 但如果不写清楚，下一个人会以为有 bug。

**教训**：加分支保护之前，先把所有「以机器人身份直接 push」的地方列出来。这次遇到的是
镜像工作流；自动化开 PR 那条走的是 `create-pull-request`，属于 PR 而非 push，不受影响。
这类改动必须和规则集**同时**完成，否则会出现「保护刚生效、流水线就断」的窗口期。

**另一个连带发现**：GitHub **不提供创建 PAT 的 API**。也就是说这一步永远需要人在浏览器
里做一次；而 fine-grained PAT 默认无法访问组织仓库，除非组织策略显式允许 —— 于是实际
可用的是 classic PAT 加 `repo` scope。

## 十五、自动化 PR 不能请求作者本人 review

**现象**：`discover` 作业在最后一步失败，前面所有步骤都是绿的：

```
##[error]Review cannot be requested from pull request author.
```

**根因**：工作流用 `reviewers:` 指定审阅人，而 PR 是用同一个维护者的 PAT 开的。
GitHub 不允许把 PR 作者设为审阅人。

**修复**：改成 `assignees:`。指派同样能把事情通知到人，且没有这个限制。

**教训**：用 PAT 开 PR 时，「谁来开」和「谁来审」必须分开考虑。若确实需要 review 请求，
就得用一个**不是** PR 作者的账号来开 PR —— 这也是为什么自动化用的令牌最好单独建一个。

## 十六、这几件事共同的排查方法

顺序比技巧重要。这一轮的顺序是：

1. **先确认红的是不是自己刚改的。** 对比失败运行对应的 commit 与 `git log` 的时间线。
   这次的红从 10-11 就开始，与当天的文档提交无关 —— 如果一开始就假定是自己改坏的，
   会白查很久。
2. **从最早的那次红开始看。** 后面的红大多只是同一个根因的重复。找到「第一次红」能
   直接把范围缩小到那一次提交。
3. **区分「作业红」与「断言红」。** 作业整体红可能只是其中一条断言。在失败日志里先找
   `##[error]`，再看它前面最后一条成功日志 —— **卡在哪一步**比错误文本更有信息量。
4. **成功日志与退出码矛盾时，信退出码。** 那说明失败在后面，别被前面的输出骗了。
5. **用真实数据回放。** 校验器那类改动，拿一个**已经合并过的历史提交**跑一遍，比构造
   测试用例更有说服力（这次正是回放 `df541ed` 才发现它会把正常提交判红）。
6. **修 flaky 要构造反例。** 限速那条改完后，特意模拟真实超速，确认新算法仍然会失败。

## 十七、这轮留下的两个待办

- **索引记录的 URL 没有定期可达性检查。** 目前只能靠人工带 `--check-urls` 跑审计。
  可以考虑加进每日流水线，让 404 在用户发现之前暴露出来。
- **`test_*` 这类负向样本没有任何自动化在用。** 它们靠人工记得才有意义。若要让它们
  真正有价值，应当在 CI 里对它们跑一遍并断言**预期的那条错误**，而不是只让它们存在。

## 十九、已装好的依赖不该再联网：一次网络抖动让装完的包“看起来失败”

**现象**：

```
🌊 Successfully installed htop@3.5.3
🌊 Binary installed to: ~/.local/macwave/bin/htop@3.5.3/htop
🌊 Link created at: ~/.local/macwave/links/htop@3.5.3
🌊 Dependency ncurses@6.6 is already installed, skipping.
🌊 Error: Cannot reach GitHub for the dependency data.
🌊   .../deps/depsinfo_arm64/ncurses/_ncurses@6.6

$ htop
zsh: command not found: htop
```

**根因分两层。**

第一层是网络：那个 URL 本身是好的（`curl` 第一次就 200），只是这条链路上
`raw.githubusercontent.com` 会间歇性地连接重置。`fetch_text` 重试三次全失败，于是报错退出。

第二层才是真正的设计问题。**依赖 `ncurses@6.6` 已经装在本地了**，代码却仍然回源取它的
版本文件。原因写在注释里：想「顺带补齐新补上的依赖边」。这个意图没错，但它把一次纯粹的
本地操作变成了网络依赖 —— 而网络恰好是整个安装里最不可靠的环节。

后果比报错本身更糟：软件包本体、带版本号的链接都已经落盘，只有**不带版本号的链接**没建
（那一步排在依赖安装之后）。于是命令报失败，二进制也真的不能直接用。

**修复**：`8512158`，已安装的依赖优先读它自己的 `_DEPS`（装好时就写在那里），只有
`_DEPS` 不存在时才回源 —— 那才说明上次安装真的中断了、需要补齐。

**验证**：修完后同样的命令一次通过，`Relocating Mach-O files in 19 installed artifact(s)`
之后正常建链接，`htop --version` 输出 `htop 3.5.3`。

**教训**：

1. **已经在本地的数据不要再走网络。** 判断顺序应当是「本地有没有 → 再考虑远端」，
   而不是「远端是权威，所以每次都问」。
2. **失败要落在干净的边界上。** 这次是「包已装好、链接没建」。哪怕修不了网络，至少应当
   在依赖步骤失败时提示「包已安装，运行 `wave link <名字>` 即可」，而不是让用户面对一个
   装完却不能用的命令。
3. **复现要靠因果，不靠运气。** 这条只有在网络抖动时才出现；先确认 URL 可达、再读代码
   找到那次多余的请求，才能确定不是数据缺失（记录其实一直都在）。
