## 一、先建立三层心智模型

读这份代码之前，先记住三个层次，后面所有细节都能挂上去。

**第一层：仓库层。** 程序代码在 `MacWave` 仓库；版本事实在 `configdata`；包数据在 `infosource`。三者完全解耦，靠 HTTP 拉取连接。

**第二层：进程层。** 用户敲 `wave`，只有一个 Python 进程在跑。它读配置、定位安装根目录、把三个代码目录塞进模块搜索路径，然后按命令表分发给某个模块的 `handle_*` 函数。所有 Python 模块共享同一个进程和同一份配置。

**第三层：脚本层。** Python 不做重活。下载完成后，Python 把一串用换行符分隔的参数拼成长字符串，交给 Bash 脚本执行真正的解压、落盘、建链接、校验、重签名。Python 负责「决定做什么」，Bash 负责「做」。

理解这三层，就能解释代码里很多看起来奇怪的写法 —— 比如为什么参数要用长字符串传而不是命令行参数，为什么有些 Python 函数只是转发给 `subprocess`。

## 二、程序仓库逐文件说明

### 2.1 仓库根目录

| 路径 | 是什么 | 维护建议 |
| --- | --- | --- |
| `lib/` | 入口、帮助、配置解析、安装与自更新脚本 | 核心，改动需测试 |
| `pkg/` | 软件包安装、查询、卸载、链接、解压、版本比较 | 核心，改动需跑端到端 |
| `surfboard/` | 依赖处理与动态库路径重写 | 最复杂，改动需跑依赖链测试 |
| `scripts/` | 回归测试与数据审计；另有 `build_portable_python.sh`（自建便携解释器，只在上游归档不可达或需要镜像时用；默认路径是直连上游） | 改核心逻辑时同步更新 |
| `docs/` | 技术手册与本文 | 随代码更新 |
| `.github/workflows/` | 持续集成与分支镜像 | 见 2.6 |
| `.templates/` | 运行时目录的样例，仅作参考 | 纯参考，不参与执行 |

| `test/` | 负向测试样本的载荷（缺 sha256 / sha256 错误），由索引里的 `test_*` 包引用 | 改名或移动会立刻让对应包 404，见 `docs/CI-AND-PITFALLS_20261018.md` 第十三节 |
| `images/` | README 演示图 | 仅文档用 |
| `PROJECT_CONTEXT.md` | 项目结构说明（偏实现细节） | 与本文有重叠，以本文为准 |
| `README.md`、`README.zh-Hans.md` | 面向用户的说明 | 发版时更新版本号与包列表 |
| `STYLE.md` | 代码风格约定 | 很短，但必须遵守 |
| `STATEMENT.md` | 贡献声明：禁止使用特定 AI 产品提交 PR | 合并前核对 |

### 2.2 `lib/` —— 入口层

这一层只负责「把用户的话翻译成某个模块的调用」，以及「MacWave 自身怎么装、怎么更、怎么卸」。

| 文件 | 职责 | 关键点 |
| --- | --- | --- |
| `wave.py` | 唯一入口。读配置、注入模块路径、按命令表分发 | 命令分发**之前**先拦下各命令的帮助请求，交给 `help.py`。否则各处理函数不认识帮助旗标，会出现「安装命令报错」「列表命令静默忽略」「自更新真的开始更新」三种坏结果 |
| `wave`（生成） | **不在仓库里**：`install.sh` / `selfupdate.sh` 生成的最外层入口，是一个 sh 启动器 | 按「私有 venv → 安装时记录的解释器 → PATH 上的 python3」挑选**真正能 import 依赖**的解释器，再 exec `wave.py`。改入口逻辑要同时改两个脚本里的 `write_launcher` |
| `configpaths.py` | 配置目录解析的唯一来源 | 系统级优先、损坏则回落用户级。另提供「路径必须位于根目录内」的安全校验，防止配置被篡改后写到任意位置 |
| `configerror.py` | 启动自检：机器上到底装没装 | 两处配置有一处有效就放行；都没装且当前在 git 仓库里时，报错并引导用安装脚本 |
| `help.py` | 三套文本：总帮助、版本信息、子命令帮助 | 子命令帮助只列该命令真正接受的旗标，不承诺做不到的事 |
| `install.sh` | 官方安装器 | 见下 |
| `uninstall.sh` | 卸载器 | 确认从终端设备读，标准输入为空时**不能**当作同意 |
| `selfupdate.py` | 自更新第一层：判断有没有新版、触发更新、复核结果 | 复核不可省，见技术手册 8.1。`--max-time` 在这里从原始命令行解析，原样经 `MACWAVE_MAX_TIME` 传给脚本，由脚本自己再解析一次 |
| `selfupdate.sh` | 自更新第二层：按清单逐文件更新 | 自带清单解析器，因为解析器本身不能依赖「还没下载的文件」。所有下载都走 `fetch_to_file`（超时 + 重试 + 先写分片再 mv），超时值由 `mw_seconds` 把 `40s`/`1min20s`/`2h` 折算成秒 |

**`install.sh` 内部的分段结构**（按执行顺序）：

1. 测试根处理（`MACWAVE_TEST` 环境变量，把任意目录当作系统根）
2. 从版本数据仓库读取版本号、发布分支、文件清单地址
3. 命令行参数解析（静默模式、目录选项）
4. 架构探测与目录菜单
5. 提权与目录创建
6. 配置与版本文件写入
7. 按清单下载程序文件
8. Python 依赖安装
9. PATH 写入 shell 配置
10. 旧版残留清理
11. Xcode 工具检查
12. 目录结构迁移（读版本数据里的迁移标记）
13. 许可协议与回滚
14. 完成提示

**`uninstall.sh` 的两个守卫**：确认从终端设备读取（空输入不当作同意）；自删前检查脚本自身是不是「含标记的普通文件」（否则文档推荐的执行方式会把解释器删掉）。

### 2.3 `pkg/` —— 软件包层

| 文件 | 职责 | 关键点 |
| --- | --- | --- |
| `pkginstaller.py` | 安装编排：解析参数与架构、定版本、取元数据、取版本记录、下载、调脚本、递归装依赖、收尾建链接 | 全流程最长的一个文件；下载器支持进度条、断点续传、限速、代理、超时重试询问、磁盘空间检查 |
| `pkginstaller.sh` | 安装入口（软件包形态） | 只做参数组装与结果落库，真正的安装动作复用依赖层的通用核心 |
| `pkgunzip.sh` | 按扩展名解压 | 八种常规格式 + conda 特殊格式；裸 xz 走 Python 标准库；conda 只取载荷、保留符号链接、挡掉危险路径 |
| `pkgversionparser.py` | 版本解析、比较、排序 | 处理预发布与社区特有后缀；约定两段与三段版本等价 |
| `pkginfohelper.py` | `list` / `search` / `info` 三个查询命令 | 需要区分「本地已装」与「远程可装」两套数据 |
| `upgrader.py` | 升级：取最新版本、复用安装流水线、按需清理旧版本 | 只做决策，真正的下载与安装交给 `pkginstaller`；「删哪些版本」的判定在这里，非交互时一律不删 |
| `uninstaller.py` | 卸载：移除版本、清理依赖、刷新链接 | 依赖清理靠反向标记判断「还有没有人用」；链接降级与悬空拒绝都在这里 |
| `linker.py` | 无版本链接的增删查 | 供安装与卸载复用，也被链接命令族直接调用 |

**这几个文件的调用关系**：安装命令进 `pkginstaller`，它装完本体后调依赖层，最后回到 `linker` 建链接；卸载命令进 `uninstaller`，它删完后同样调 `linker` 刷新；查询命令进 `pkginfohelper`。

### 2.4 `surfboard/` —— 依赖与二进制修复层

这是全项目最复杂、也最容易出隐蔽 bug 的地方。

| 文件 | 职责 | 关键点 |
| --- | --- | --- |
| `depsinstaller.py` | 依赖安装编排：解析依赖声明、判断是否已装、拉取依赖数据、递归安装、打标记、最后触发路径重写 | 递归顺序是「先装下层再装自己」；已装依赖只补标记，不重复下载 |
| `depsinstaller.sh` | 依赖安装入口（整树形态） | 与 `pkginstaller.sh` 共用同一套安装核心 |
| `depsmanager.sh` | **通用安装核心**，被上面两个脚本引入，不单独执行 | 定位文件、校验、解压、按形态落盘、建链接、写依赖清单；两种形态的唯一区别就在这里 |
| `depsversionparser.py` | 解析依赖引用、比较依赖版本 | 版本比较复用软件包那一套，避免规则漂移 |
| `querier.py` | 判断某个依赖的某个版本是否已装 | 只读，无副作用 |
| `tagger.sh` | 管理依赖目录下的反向标记文件 | 创建、删除、查询「谁依赖了我」 |
| `transfer.sh` | Mach-O 动态库引用重写 + 重签名 | 幂等；只处理 Mach-O；系统库不动；按「产物自身 → 依赖清单 → 其余依赖」的顺序解析 |

**为什么 `depsmanager.sh` 是核心。** 软件包与依赖看起来是两种东西，但落盘动作几乎一样：校验、解压、找到要保留的内容、建链接、写清单。区别只有两点 —— 软件包只取一个可执行文件，依赖保留整棵树。把这套逻辑抽成一份，避免两处实现漂移。

### 2.5 `scripts/` —— 回归与审计

这些脚本**不参与运行时**，只在开发与 CI 时使用。

| 文件 | 用途 |
| --- | --- |
| `random_test.py` | 随机抽包做端到端回归（安装 → 运行 → 卸载），发现面最广 |
| `deps_test.sh` | 依赖链端到端：装带依赖的包 → 运行 → 检查标记 → 卸载 → 确认级联清理 |
| `link_test.sh` | 无版本链接全生命周期回归 |
| `format_test.sh` | 逐个压缩格式的安装/执行/卸载（九个归档格式 + 一个无扩展名样本，共十个测试包） |
| `selfupdate_test.sh` | 自更新：版本解析、短路、跨大版本拒绝、同大版本端到端（最后一步会真的更新，所以放最后） |
| `sandbox_test.sh` | 安装器/卸载器在系统沙箱里跑，宿主除沙箱外零写入，且离线 |
| `configpath_test.sh` | 配置目录解析的优先级与容错回落 |
| `audit_deps.py` | 数据审计：检查数据完整性，或把已装产物的实际动态库引用与声明对比 |

**所有测试共享的隔离机制**：设置 `MACWAVE_TEST` 指向一个临时目录后，安装器、卸载器与相关脚本会把该目录当作系统根，家目录也挂到它下面。危险操作必须用它。

### 2.6 `.github/workflows/`

| 文件 | 作用 |
| --- | --- |
| `format-test.yml` | 在多个 Python 版本上跑格式与回归；分支列表里包含若干历史分支 |
| `sync-release-branch.yml` | 主分支与发布分支的自动镜像，只做快进，分叉即报错 |

镜像工作流用**属于组织管理员的令牌**推送，因为机器人身份无法进入分支保护的豁免名单。它触发的第二次运行会发现两侧已相等而退出，不构成循环。

### 2.7 `.templates/`

运行时目录的样例文件，用来给人看「装完之后长什么样」，**不参与任何执行流程**。里面的占位包和配置文件仅作示意。

## 三、用户端目录详解

MacWave 装完之后，机器上会有两类目录：**代码树**（安装根目录）和**配置目录**。理解它们的区别，能解决大半「我明明装了却读不到」的问题。

### 3.1 安装根目录

这是所有代码与产物的家。下面七个目录各有明确分工：

| 目录 | 含义 | 谁写它 |
| --- | --- | --- |
| `bin/` | 已安装的软件包，每个包每个版本一个子目录 | 安装核心 |
| `deps/` | 依赖树，按「依赖名/依赖名@版本号」两层展开 | 安装核心（整树形态） |
| `links/` | 所有命令入口的软链接集中在这里，**已在 PATH 上** | 安装核心、链接模块 |
| `venv/` | **私有 Python 虚拟环境**（3.0.6 起）：`requests` / `packaging` / `rich` 装在这里，与系统 Python 升级解耦 | 安装器、自更新 |
| `python/` | **自带的便携 CPython**（3.0.6 起）：`<版本>/` + `current` 符号链接。入口默认用它，因此用户机器上的 `python3` 由谁接管都不影响运行 | 安装器、自更新 |
| `lib/` | 入口、帮助、配置解析、安装与自更新脚本 | 安装器、自更新 |
| `pkg/` | 软件包处理模块，以及已安装包数据库 | 安装器、自更新、安装核心 |
| `surfboard/` | 依赖处理与路径重写模块 | 安装器、自更新 |
| `downloads/tmp/` | 下载缓存与断点续传文件 | 下载器 |

**为什么 `links/` 要单独存在。** `bin/` 下的目录名带版本号，直接放进 PATH 也能用，但用户要敲带版本号的命令，体验很差。所以所有真实可执行文件都在 `links/` 里有一条带版本号的链接，用户的 PATH 指向 `links/`。这样「带版本号精确调用」与「不带版本号跟随默认」就统一在同一层解决。

### 3.2 包目录内部

一个已安装的软件包目录里，除了解出来的二进制，还有两类元数据：

- 一个记录「我依赖谁」的清单文件，一行一个带版本的引用
- 可能被依赖方写入的反向标记（记录「谁依赖我」）

依赖目录结构相同，但因为保留整棵树，还额外有库目录、头文件目录、资源目录。

### 3.3 配置目录

两处，系统级与用户级，各含两个文件：安装根目录记录、版本信息记录。

| 安装级别 | 配置写在哪 |
| --- | --- |
| 系统级（系统路径、家目录之外的自定义路径） | 系统级配置目录 |
| 用户级（家目录之内的路径） | 用户自己的配置目录 |

**读取规则是系统级优先，且带容错**：系统级文件存在但内容损坏、或缺少安装根目录字段时，同样回落到用户级。

这个规则是历史遗留，也是 2.5 之前那个经典故障的成因 —— 残留的旧系统级配置会永久遮蔽新写的用户级配置。今天迁移逻辑会自动处理，但手工排查时仍要**两处都看**。

### 3.4 已安装包数据库

安装根目录的程序目录里有一个数据库文件，记录每个包的版本、二进制路径与安装时间，写入时加文件锁。

它和包目录是两套记录：包目录是事实（文件在不在），数据库是索引（快速列举）。两者不一致时以包目录为准，数据库可由重装重建。

### 3.5 `MACWAVE_TEST` 隔离根

设置这个环境变量后，安装器与相关脚本会把指定目录当作系统根，家目录也挂到它下面。所有系统路径都变成该目录下的相对路径。

用途：复现迁移、测试安装器、跑危险实验。**这是唯一安全的实验方式**，因为它保证不碰真实系统。

## 四、版本数据仓库（configdata）

这个仓库只有三样东西，但每一样都直接影响安装与升级。

### 4.1 目录结构

| 路径 | 作用 |
| --- | --- |
| `versiondata/latest_version` | 最新版本号、发布日期、构建号、发布分支、更新命令 |
| `versiondata/files_info` | 要下载的程序文件清单（缩进树） |
| `versiondata/latest_test_version` | 测试用版本文件，内容为空，仅占位 |
| `updatedata/{版本号}/dir_structure_change` | 单字符标记，表示该版本是否改了目录结构 |
| `updatedata/{版本号}/transfer_commands` | 为真时执行的迁移脚本 |

### 4.2 约定

**版本号目录必须逐个补齐。** 查找只按「正在安装的完整版本号」进行，所以 3.0 的迁移脚本要在 3.0、3.0.1、3.0.2、3.0.3、3.0.4 各放一份。脚本本身幂等，重复放置无副作用。

**标记文件的三种状态要分清**：存在且为真 → 执行迁移；拉不到或不存在 → 按「没改」静默跳过；标记为真但脚本拉不到 → 报错退出。最后一条是为了避免半迁移状态。

**迁移脚本自己判断要不要动手。** 调用方只通过环境变量告诉它安装目录、配置目录、目标版本，不做业务判断。这样同一份脚本能安全地放在多个版本目录下。

**清单只写仓库内路径。** 不要写绝对路径，也不要在清单之外硬编码文件。新增程序文件只改这份清单，两个脚本都不用动。

### 4.3 谁在读它

安装器读版本号、发布分支与清单；自更新第一层读版本号与更新命令；自更新第二层读清单与迁移标记。**没有任何代码把它写死**，这是刻意的。

## 五、包索引仓库（infosource）

### 5.1 目录结构

| 路径 | 作用 |
| --- | --- |
| `pkg/pkginfo_arm64/` | Apple 芯片的软件包记录 |
| `pkg/pkginfo_amd64/` | Intel 的软件包记录 |
| `deps/depsinfo_arm64/` | Apple 芯片的依赖记录 |
| `deps/depsinfo_amd64/` | Intel 的依赖记录 |
| `scripts/` | 索引自动化脚本（扫描、校验、发布说明） |
| `docs/` | 自动化说明 |
| `fill_deps.py` | **历史遗留**的批量填充脚本，内含写死的本地路径，不可运行 |
| `.github/workflows/` | 每日索引更新流水线 |

两种架构的包数量应当一致（当前各 37 个），出现差异通常意味着某一边漏了记录。

### 5.2 记录文件的命名约定

每个包是一个目录，目录里两类文件：

- `_{名字}@common` —— 元数据
- `_{名字}@{版本号}` —— 某个具体版本

依赖目录完全平行，只是元数据里记录的是依赖名而非可执行文件名。

**命名必须三处一致**：目录名、记录文件名里的名字、记录文件名里的版本。校验器会检查目录名与记录名是否匹配。

### 5.3 字段约定

元数据记录：说明、主页、许可证、作者、可执行文件名（依赖则是依赖名）。

版本记录：下载地址、校验值，可选依赖声明。

约束：地址必须 HTTPS；校验值必须 64 位小写十六进制；依赖声明是多行形式、首行带前缀、后续行缩进对齐；无依赖就不写该字段。

**元数据记录不含地址与校验值** —— 这是一条重要的隐含约定，所有校验工具都必须显式跳过这类文件，否则会把全部元数据判成非法。

### 5.4 测试包约定

以特定前缀开头的包是**故意不合法**的测试样本（例如故意缺校验值、故意写错校验值）。它们用于验证安装器的错误处理。

因此校验工具必须跳过这一前缀，否则永远红。这是本项目的一条硬约定。

### 5.5 自动化流水线

每日定时扫描上游发布页，只处理「下载地址指向 GitHub 发布页 + 版本号纯数字 + 无依赖声明」的包。产物匹配要求架构、平台、文件名形状三者同时唯一。结果写到专用分支并开待审 PR，合并且正文含隐藏标记时才发索引更新发布。

**跳过而不是猜测**是这套逻辑的核心原则：conda 包、自定义镜像、带依赖的记录、歧义产物、非数字标签、测试包，一律跳过并把原因写进运行摘要。

## 六、代码风格与约定

风格文件很短，但有几条是硬性的。

### 6.1 Python 文件头

所有 Python 文件前四行固定：解释器声明、空行、以注释形式写的文件名、空行。第五行起才是代码。

这个约定的实际价值是：用编辑器搜索文件名时，文件头能立刻告诉你「我在哪个文件里」，尤其是在多个模块函数名相似的情况下。

### 6.2 分区注释

长文件用横线包裹的分区标题组织，常见分区依次是：颜色定义、参数与检查、主逻辑、入口。

### 6.3 输出约定

- 所有面向用户的输出带波浪前缀
- 错误用粗体红色，打印后以非零码退出
- 警告用黄色，成功用绿色
- 颜色常量在模块级定义，名字固定（红、绿、黄、重置四件套）

### 6.4 Shell 脚本约定

- 普遍使用 `set -e`（安装器用更严格的 `set -eE` 加错误陷阱）
- 颜色定义与 Python 侧保持同名的四件套
- 脚本之间不通过命令行参数传复杂数据，而通过**换行分隔的长字符串**

### 6.5 为什么用长字符串而不是参数

安装核心需要接收十几项信息（名称、版本、校验值、目标目录、安装根、可执行文件名、依赖者、原文件名等）。用命令行参数会很长且易错位；用环境变量会污染子进程；用临时文件又要管理生命周期。

换行分隔的长字符串是这里最实用的折中：Python 侧按顺序拼接，Bash 侧按行读取，顺序即契约。代价是**顺序一旦改变必须两边同时改**，这是修改这些接口时最容易踩的坑。

### 6.6 命名与语言

代码注释与用户可见文本以中文为主，标识符用英文。新增代码应保持这个习惯。

### 6.7 提交与贡献

仓库根目录的声明文件明确禁止使用特定 AI 产品提交 PR。合并前需核对。

## 七、跨模块接口约定

这部分是「接手的人最容易改坏」的地方，单独列出。

### 7.1 命令分发契约

入口维护一张命令表，每个命令映射到一个处理函数。所有处理函数接收**原始命令行字符串**而不是解析好的参数列表 —— 因为各命令的旗标集合不同，统一在这里解析会互相污染。

### 7.2 配置解析契约

只有配置解析模块可以读配置文件。其他模块一律调用它提供的函数，不得自己拼路径。这样「系统级优先 + 容错回落」的规则只有一处实现。

### 7.3 安全边界契约

凡是根据配置或用户输入拼接出来的路径，在删除或写入前必须做「位于根目录内」的校验。这条规则是为防止配置被篡改后把文件写到任意位置。

### 7.4 安装核心契约

安装核心接收长字符串与依赖列表，返回落盘结果。它不判断「该不该装」——那是编排层的职责。它只保证：校验失败即中止、解压失败即中止、落盘后链接与清单一定写入。

### 7.5 依赖标记契约

三类记录必须同步维护：自己的依赖清单、对被依赖者的反向标记、以及卸载时的清理顺序。任何一处漏写都会导致「依赖被提前删掉」或「依赖永远删不掉」。

### 7.6 路径重写契约

重写必须发生在**全部产物就位之后**，且必须幂等。任何在安装中途调用它的改动都是错误的 —— 目标库可能还没落盘。

## 八、历史遗留与不要动的东西

接手时最容易被误导的部分，单列出来。

| 路径 | 状态 | 说明 |
| --- | --- | --- |
| `.Pseudocode/` | 废弃 | 早期伪代码，与现有实现不一致，不要作为参考 |
| `infosource/fill_deps.py` | 不可运行 | 内含写死的旧本地路径，仅记录当年的填充方式 |
| `configdata/versiondata/latest_test_version` | 空文件 | 占位，测试流程读取 |
| 历史分支上的旧实现 | 只读参考 | 1.x 是单文件、2.x 是平铺文本索引，与现在完全不同 |
| `docs/CI-AND-PITFALLS_20261012.md` | 归档快照 | 与主文档并存，内容是某一时点的踩坑记录 |
| `.codex/`、`.pycharm/`、`.vscode/` | 编辑器配置 | 与运行无关 |

**另外两条不要动的东西**：

旧数据分支（`legacy-infosource`、`legacy-configdata`）已被改名，3.0 之前的客户端会因此取不到数据。这是有意的行为，不要「修复」它。

`.templates/` 里的占位文件不参与执行。修改它们不会影响任何行为 —— 如果发现代码读了它们，那是 bug。

## 九、新读者阅读路线

按这个顺序读，能最快建立完整印象。

**第一遍：走通一条命令。** 从入口文件开始，看命令表；找到安装命令对应的处理函数；跟着它走完「解析参数 → 定版本 → 取元数据 → 下载 → 调脚本 → 装依赖 → 建链接」。走完这一条，整个项目的骨架就清楚了。

**第二遍：只看依赖层。** 依赖安装的递归、标记的三种记录、以及最后那次路径重写，是项目里逻辑密度最高的部分。建议配合依赖链测试脚本一起读。

**第三遍：读数据仓库。** 版本数据的三个文件与索引仓库的记录格式。这两处决定了「加一个包」和「发一个版本」怎么做，是日常维护的主要工作面。

**第四遍：读安装器。** 它最长，但结构是线性的，按执行顺序读即可。重点看测试根处理、配置写入、迁移调用、失败回滚四处。

**遇到不懂的行为时，先问三个问题**：这个行为是谁决定的（代码、版本数据、还是索引数据）；它发生在安装期还是运行期；它是否与历史迁移有关。这三个问题能定位绝大多数「为什么是这样」。
