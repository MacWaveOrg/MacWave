## 一、MacWave 是什么

MacWave 是一个面向 macOS 的包管理器，主要托管 iOS、iPadOS 与越狱生态相关的命令行工具，同时也收录常见的通用 Unix 工具。它用 Python 写主逻辑，用 Bash 做安装、解压与二进制搬运，没有编译步骤 —— 安装下来的代码树本身就是可运行的源码。

它和 Homebrew 的根本差别在**安装模型**。Homebrew 给每个包一个独立前缀目录，再通过符号链接把可执行文件挂进统一位置。MacWave 则是把每个包的每个版本都保留成一个独立目录，目录名带版本号；所有可执行文件都通过一个集中式链接目录进入 PATH。这个差别带来两个直接后果：多个版本天然并存，切换默认版本只是改一条链接；升级或降级不会破坏旧版本，回滚不需要重新下载。

MacWave 的设计目标不是取代通用包管理器，而是应付一类 Homebrew 很难处理的场景 —— 上游只提供预编译二进制、依赖关系靠运行时动态链接而非编译期声明、需要把整个依赖树塞进一个自包含目录。越狱工具链恰好全中。

## 二、仓库分工

MacWave 不是一个仓库，而是一组职责分离的仓库。理解分工是理解其余一切的前提。

**程序代码仓库**（`MacWaveOrg/MacWave`）承载入口、安装、卸载、查询、链接、自更新等全部逻辑。它的 `main` 分支与当前发布分支（今天叫 `3.0`）保持逐提交镜像，两者内容始终一致，区别只在于 `main` 是开发主线、发布分支是版本锚点。

**版本数据仓库**（`MacWaveOrg/configdata`）只放版本事实：最新版本号是多少、发布分支叫什么、这次版本要下载哪些程序文件、以及升级时需不需要跑目录结构迁移。安装器和自更新都从这里取信息，所以发版不需要改代码。

**包索引仓库**（`MacWaveOrg/infosource`）是纯数据：每个包和每个依赖的元数据、下载地址、校验值、依赖声明。安装、搜索、详情查询都实时读它，没有本地缓存。

**官网仓库**（`MacWaveOrg/Pages`）只服务 `macwave.org`。

**历史快照仓库**（`MacWaveOrg/legacy-MacWave`）已归档为只读，只为留存旧实现。

4.0 新增两个**二进制仓库**，把「从别人服务器下载」换成「从自己这里下载」：
`MacWaveOrg/Bottle` 放预编译的软件包，`MacWaveOrg/Deps` 放依赖库。
同时自更新数据从 `configdata` 挪到 `MacWaveOrg/Selfupdate` —— 它的发布节奏与
「安装信息」不同，混在一起时每次发版都要改两个语义不同的地方。
`configdata` 在 4.0 起只为 3.x 保留，不再接收新版本。

此外，程序代码仓库里还保留两条改名后的旧数据分支，分别叫 `legacy-infosource` 和 `legacy-configdata`。它们在 3.0 之前存放包索引与版本数据，3.0 起被独立仓库取代。改名是有意的：3.0 之前的老客户端会因此取不到数据，从而暴露「你该升级了」，而不是悄悄拿到已经变了结构的数据。

**为什么数据要独立成仓库。** 数据更新频率远高于代码 —— 上游发版随时可能发生，一天加好几个包是常态。把数据剥离出去，加包就不必碰程序代码，也因此能做权限分级：自动化可以对数据仓库提 PR，而程序代码保持人工把关。

## 三、版本谱系（含已废弃版本）

MacWave 从 2026 年 8 月初起，两个多月内走完了 1.0 到 3.0。这段演化速度很快，留下的痕迹至今仍是许多行为的成因。

### 3.1 总览

| 版本线 | 时间 | 代码形态 | 数据在哪 | 状态 |
| --- | --- | --- | --- | --- |
| **1.0 / 1.1** | v1.0.0 于 2026-08-16，v1.1.0 于 08-22 | 单文件脚本 | 仓库内一个 JSON 索引 | 已废弃 |
| **2.0.0-beta / dev** | 2026-08-22 | 拆出模块目录 | 按架构分文件的平铺文本 | 已废弃 |
| **2.1.0** | 2026-08 起 | 引入依赖处理目录 | 平铺文本 | 已废弃 |
| **2.2 ~ 2.4** | v2.2.0 于 09-22，v2.4.0 于 09-28 | 依赖体系成型 | 平铺文本向分支迁移 | 已废弃 |
| **2.5 ~ 2.6.1** | v2.5.0 于 10-05，v2.6.1 于 10-07 | 自更新、软链接、路径重写齐备 | 程序仓库的 `infosource` 分支 | 已废弃，2.x 终点 |
| **3.0 ~ 3.0.4** | v3.0 于 10-08，v3.0.4 于 10-12 | 结构稳定 | 独立的数据仓库 | 当前维护 |

版本标签保存在程序仓库里，含各版本的语义化标签，以及后来为索引更新单独打的日期序号标签。

### 3.2 1.x：单文件时代

1.x 的整体逻辑装在一个脚本里，包索引是一个 JSON 文件，仓库里另有测试目录与早期的预发布目录。那个阶段的设计假设是：包少、没有依赖、每个包就是单个可执行文件。于是下载、校验、解压、放进 PATH 全部写在同一个流程里。

随着包变多、开始出现需要整棵目录树的库依赖，这个假设崩了。单文件无法承载依赖递归，也无法表达多架构元数据，更难做「同一个包的多个版本并存」。1.x 因此被整体重写，而不是修修补补。

### 3.3 2.0 ~ 2.1：模块化起步

2.0 把逻辑拆进若干目录：入口与帮助、包处理、以及后来的依赖处理。包索引从单文件 JSON 改成按架构分开的平铺文本，每行描述一个包。这个时期还短暂用过 Ruby 解析包数据，后来全部改回 Python。

2.1 首次出现完整的依赖处理模块和一批脚本与工程规范文件，也首次出现了版本解析器与解压脚本的分离。

这一代的问题是数据模型太薄：平铺文本没有目录级元数据，无法把描述、主页、许可证这类信息与版本记录分开；也无法为同一个包的不同架构放不同内容；测试包与正式包混在一起，没有区分手段。

### 3.4 2.2 ~ 2.4：依赖体系成型

这几个版本把重心放在依赖上。依赖改为「整棵解压目录保留」而不是只取一个文件 —— 因为库包必需如此。同时引入三类记录文件：产物自己声明依赖谁、以及两种反向标记记录谁依赖了我。这三者共同支撑起级联卸载：只有当某个依赖不再被任何人标记时，才会连同它自己的依赖一起删除，共享依赖不会因为卸载其中一个使用者而被误删。

这段时间也补上了不带版本号的软链接命令族，以及依赖目录里的动态库搬运脚本。

### 3.5 2.5 ~ 2.6：最后一个 2.x

2.5 是一次结构性变更，也是理解今天配置行为的关键。

在此之前，所有安装都把配置写在系统级位置。读取规则是「系统级优先、找不到再回落用户级」。这导致一个隐蔽的故障：如果用户做的是用户级安装，但机器上残留了旧的系统级配置，那么新写的用户级配置会被旧配置永久遮蔽 —— 程序看起来装好了，实际读的是一个早就该废弃的目录。

2.5 把配置位置改成跟随安装级别：系统级安装仍写系统级位置，用户级安装写用户自己的配置目录。同时补上一段迁移逻辑，专门把旧版遗留的系统级配置搬到用户级位置，并且连配置文件本身一起搬 —— 否则程序会认为「没装」。

2.5 还引入了自更新的两层结构：一层是判断有没有新版本并触发更新，另一层是真正按清单拉取文件。这个分离是为了解决一个先有鸡还是先有蛋的问题：更新脚本不能依赖「还没下载下来的新文件」，所以必须自带解析能力。

2.5 线上先后发布了若干补丁与次版本，终点是 2.6.1。

### 3.6 3.0：数据外置

3.0 的核心变化不是功能，而是把数据从代码仓库剥离到独立仓库，并顺带把版本号与文件清单也搬了过去。这让「发版」和「加包」彻底解耦。

同时补上一条硬性规则：跨大版本不允许自更新。原因是每个大版本通常会同时改代码结构与目录结构，局部替换文件无法保证一致性。这条规则写在发布分支的自更新脚本里，所以随新版本下发，不需要在数据仓库里逐版本配置。

3.0 的版本标签从 v3.0 一路到 v3.0.4。

### 3.7 废弃版本还能用吗

不建议，实际也大概率不可用，原因有三层。

第一层是数据断了：旧客户端读的是程序仓库里的旧数据分支，那些分支已改名为 `legacy-` 前缀。

第二层是能力不足：没有目录级元数据、没有现代压缩格式支持、没有动态库路径重写，装今天的包会在解压或加载阶段失败。

第三层是自更新的历史缺陷：2.5 之前的自更新把版本文件路径写死。配置被迁移走之后，升级完成时的复核会读不到文件，从而误报「更新失败」——而实际上已经成功了。这个误报曾让不少人反复重装。

保留这些版本的唯一价值是查阅历史实现。若确需复现，应当从标签检出到隔离环境里跑，不要装到真机。

## 四、安装与运行时目录

### 4.1 安装做了什么

官方安装是一条单行命令，从程序仓库拉取安装脚本执行。脚本会依次完成这些事：选安装目录、按需提权、建运行时目录、写配置文件、按版本数据里的文件清单把全部程序文件下载到位、**取回自带的便携 Python**（校验 sha256 后解包到 `python/`，失败则回退系统解释器）、用它建私有环境并安装三个 Python 依赖（网络请求库、版本比较库、终端渲染库）、把三个目录写进 shell 配置的 PATH、清理旧版平铺安装的残留、检查 Xcode 命令行工具是否齐备、展示许可协议、最后写版本文件并宣告完成。

几个容易被忽略但很重要的细节。

**文件清单与自更新共用。** 安装和自更新读的是同一份清单，由版本数据仓库提供。因此新增程序文件只需要改那份清单，不需要改任何一个脚本 —— 这是刻意的设计，避免两处清单漂移。

**失败时不自动清理。** 安装中途失败会打印已下载内容的路径并提示重跑，但不会自动删除。原因是删除不可逆，而下载内容重跑即可复用。

**许可协议排在最后。** 拒绝时会把安装树、配置目录以及 shell 配置里的 PATH 一起回滚，回滚过程不会写死提权方式。

**无人值守安装。** 提供静默模式，全程不交互；未指定目录选项时使用默认项。静默模式需要免密提权，否则会明确报错退出，而不是卡在密码提示上。

### 4.2 安装目录

菜单项随 CPU 架构变化。Apple 芯片提供两个选项：家目录下的用户级目录，以及系统级目录。Intel 机器多一个系统级推荐路径。最后一项永远是自定义目录。

自定义目录的级别按位置判定：在家目录之内算用户级，之外算系统级。这个判定直接决定配置文件写到哪里，进而影响 2.5 那个历史坑是否会被触发。

Apple 芯片上不提供那个 Intel 专属路径，因为该目录在新版 macOS 上归系统管理，写入它容易与系统完整性机制冲突。

### 4.2.1 解释器从哪来（3.1 起）

3.0.x 及更早，入口脚本第一行指向 PATH 上的 `python3`，而依赖是用安装时那个 `pip3` 装的。
两段「当时」一旦不一致（例如 Homebrew 把 `python3` 从 3.14 换成 3.15），所有命令都会
以「模块不可用」的形式失败 —— 这不是假设，是真实发生过的一次故障。

3.1 起，解释器由 MacWave 自己提供。4.0 把它移到独立仓库 `MacWaveOrg/Python`
（`MACWAVE_PYTHON_DOMAIN`），分两个文件：

- `pythondata/latest.toml` —— 现在该用哪个版本；
- `pythondata/<版本>/python_url.toml` —— 各架构的上游地址与校验值，
  形如 `[arm64] arm64_url / arm64_sha256`。

安装与自更新**先读 `latest.toml`，本机已有该版本且能跑就直接用，一个字节都不下**；
只有对不上时才读 `python_url.toml` 下载、校验 sha256、解到 `python/<版本>/`。
先问一次是必须的：否则「本机已有 3.14.9」会让升级到「要求 3.15」的版本时永远发现不了
自己落后。默认从我们自己的存储取那一份字节，`--install-python-from-source` 才回上游取
（两条路径共用同一个 sha256，因为字节原样搬运、文件名取上游 URL 末段）。

再用它创建私有虚拟环境。入口 `lib/wave` 是一个 sh 启动器，按「私有环境 → 自带解释器 →
安装时记录的解析器 → PATH」依次挑选**真正能 import 到依赖**的那一个。

**字节原样搬运，不重新打包。** `python_url.toml` 里的地址填的是
`astral-sh/python-build-standalone` 的 `install_only` 产物：解压后解释器就在
`python/install/bin/python3`，而安装器的探测列表里本来就有这个位置，末了还会归一化成
`python/<版本>/bin/python3` 供启动器使用。我们自己托管的那份就是同一批字节，所以校验值
可以共用。自己再 repack 一遍只能省掉一层目录名，却要多搬几十 MB、多维护一个托管
位置。校验值不采信上游的自述，由流水线下载后自己算一遍，同时确认压缩包里确实有那个路径，
然后把结果写成版本数据仓库的 PR。

**布局要归一化。** 上游产物、以及可能的自建产物，解释器深度各不相同，而启动器只认
`python/current/bin/python3` 这一条路径。所以装好之后会在 `<版本目录>/bin/python3` 补一个
**相对**符号链接指向真正的解释器 —— 相对是为了整个 `python/` 目录被搬走以后仍然有效。
少了这一步，自带解释器在启动器里永远命中不了，只有私有虚拟环境能救场；一旦虚拟环境坏掉，
就等于没有自带解释器。

取舍与 Homebrew 在 macOS 上的做法一致：它无论系统自带什么版本，都使用自己 vendor 的那份
Ruby。理由是同一个 —— 只有固定的解释器才能让报错可复现。

### 4.3 运行时目录形态

安装根目录下有六个功能目录：存放程序入口与帮助的代码目录、存放安装核心与查询逻辑的代码目录、存放依赖处理与路径重写的代码目录、存放已安装包（每个包每个版本一个目录）的目录、存放依赖树（每个依赖一个子目录、再按版本分层）的目录、以及一个集中式链接目录。另有一个下载临时目录用于断点续传，以及两项与 Python 有关的东西（3.0.6 起）：一个**自带的便携 CPython 目录**（`<版本>/` 加 `current` 链接），以及用它在旁边建出来的**私有虚拟环境**。三个依赖装进虚拟环境，而解释器来自自带的那一份 —— 因此用户机器上的 `python3` 归谁管、升到哪个版本，都不会影响已安装的 MacWave。

PATH 里实际加入的是三个：已安装包的目录、链接目录、入口代码目录。链接目录是关键 —— 已安装包目录名带版本号，直接进 PATH 并不好用，所以真正的命令入口全部以链接形式集中在链接目录里。

### 4.4 配置文件

配置目录有两处，系统级与用户级。目录里有两个文件：一个记录安装根目录，一个记录版本信息。安装级别决定写哪一处。

解析规则是系统级优先。系统级配置存在但内容损坏、或缺少安装根目录字段时，同样回落用户级。这个「优先 + 容错」的组合是 2.5 之前遗留下来的，也是很多「我明明装了却读不到」问题的根源。

已安装包的数据库在安装根目录下的程序目录里，记录每个包的版本、二进制路径与安装时间，写入时加文件锁，避免并发安装互相覆盖。

### 4.5 卸载

卸载会读两处配置定位安装根目录，两处都读不到时遍历候选路径。确认删除后，移除安装目录、两处配置目录、shell 配置里的 PATH 行，最后自删。

确认从终端设备直接读取，而不是标准输入。这一点很关键：当标准输入是空的时候，绝不能把「没有输入」当成同意，因为删除不可逆。因此无人值守场景必须显式传强制参数。

自删有守卫：只有当脚本自身是一个含特定标记的普通文件时才删除自己。原因是文档推荐的执行方式下，脚本路径变量指向的是解释器而不是脚本文件，旧写法会把系统解释器删掉。

另有一个参数纯粹为与姊妹项目保持参数兼容而存在，在 macOS 上不做任何事，因为 MacWave 没有专用账号。

## 五、数据源与记录格式

### 5.1 版本数据

版本数据仓库的核心是三个文件与一个目录。

**最新版本文件**声明四件事：版本号、发布日期、构建号、发布分支，另外还有一条更新命令。更新命令里用一对三尖括号包住真正要执行的命令，自更新会提取括号之间的内容交给 shell 执行。之所以这样绕一层，是为了让「目标版本」与「目标分支」能作为环境变量传下去，而不是硬编码在脚本里。

**文件清单**是一棵缩进树，只写仓库内路径。约定是：缩进每层四个空格、制表符等价；以斜杠结尾表示这是目录、只创建不下载；井号开头是注释；也可以跳过缩进直接写完整路径。安装器与自更新都用同一套解析规则。

**更新数据目录**按版本号分目录，每个目录里最多两个文件。一个标记文件只有一个字符，表示这次升级有没有改目录结构；另一个是迁移脚本，只在标记为「改了」时执行。标记拉不到就按「没改」静默跳过；但标记说改了、迁移脚本却拉不到，会直接报错退出 —— 宁可失败，也不留下半迁移状态。

执行迁移脚本前会通过环境变量告诉它三件事：安装目录、准备写入的配置目录、目标版本。脚本据此自行判断要不要动作，例如只对用户级安装做搬迁。

补丁版本也要各放一份迁移脚本，因为查找只按「正在安装的完整版本号」进行。迁移脚本本身是幂等的，重复放置没有副作用。

**迁移之后必须重新解析配置目录。** 因为脚本可能把配置搬走。自更新的两层结构里，第二层会在迁移后重新解析一次；第一层的升级后复核也必须每次重新解析，不能复用进程启动时缓存的路径。

### 5.2 包索引

包索引仓库的结构按「架构 → 包名 → 记录文件」三层展开，依赖索引是平行的另一套。

每个包有两类记录。**元数据记录**描述包本身：一句话说明、主页、许可证、作者、可执行文件名。**版本记录**描述某个具体版本：下载地址、校验值、以及可选的依赖声明。依赖索引的版本记录格式相同，只是元数据里记录的是依赖名而非可执行文件名。

几个不可违反的约定：下载地址必须是 HTTPS；校验值必须是 64 位小写十六进制；依赖声明是多行形式，第一行带前缀，后续行缩进对齐，一行一个「名字@版本号」；没有依赖就完全不写这个字段。

元数据记录里没有下载地址与校验值，这一点直接影响校验工具的设计 —— 校验器必须显式跳过元数据文件，否则会把所有元数据判成非法。

架构维度是一等公民。同一个包在两种架构下是两条独立记录，可以装不同的产物、带不同的依赖。这既是灵活性，也是很多「某个架构装不上」问题的来源：两个架构的记录必须分别正确，任何一边写错都只会影响那一边。

### 5.2.1 4.0 起：`url` 不再被读取，文件名进索引

3.x 的版本记录只有 `url` 与 `sha256`，客户端拿 `url` 去上游下载。4.0 改成从
`Bottle` / `Deps` 取，于是记录多了一个 `file` 字段：

```
sha256: "…"
file: "jq-macos-arm64"
url: "https://github.com/…/jq-macos-arm64"     # 保留，4.0 不读
```

`file` 是上游那份文件的名字。客户端只从它取**扩展名**，然后把产物命名成
`<名字>@<版本>.<架构><扩展名>`。字节原样搬运、不重打包，所以校验值与上游公布的一致，
可以直接用官方 SHA256。扩展名决定用哪个解压器（`pkgunzip.sh` 靠它选 `zip` / `tar.gz` /
`tar.bz2` / `tar.xz` / `conda`，没有扩展名则按裸可执行文件处理），所以**不能省略**。

架构必须写进文件名，因为 `arm64` 与 `amd64` 是两条同名同版本的索引记录，否则会撞名：

```
jq@1.8.2.arm64
jq@1.8.2.amd64
```

`url` 仍然保留，原因有两个：2.x-3.x 的客户端还要用它；想知道上游来源的人也要看它。
4.0 只在一种情况下读它 —— `wave install <包> --install-from-source`，绕开我们自己的
存储直接回上游装（依赖也一并回上游）。这个旗标只有长参数，没有短参数。

### 5.2.2 二进制存在哪

产物存放在 `Bottle` / `Deps` 两个仓库的 **Release** 里，一个包一个 tag：

```
tag   = 包名
资产名 = <包名>@<版本>.<架构><扩展名>
```

客户端拼出来的地址：

```
https://github.com/MacWaveOrg/Bottle/releases/download/jq/jq%401.8.2.arm64
```

选这个形状的**唯一标准**是「国内镜像站要能用 rsync + nginx 原样提供」——实测从大陆连
`github.com`，三次里两次在 20 秒内连 TCP 都没建立，同一时刻国内镜像站 37~78 ms 就返回了，
所以镜像不是优化项而是必需品。而镜像站能提供的只有普通文件树：

- **容器 registry（GHCR）不行**：它按 digest 取字节、要先换 token，静态服务器模拟不了；
- **git 仓库里的文件不行**：单文件超过 100 MiB 直接拒绝推送，而 `ollama-darwin.tgz`
  已经是 172.9 MB；
- **Release 可以**：单文件 2 GiB，官方明确不限制总量与下载带宽，且下载路径
  `/<tag>/<资产>` 与镜像站的 `/<包名>/<文件名>` 在域名之后完全相同——换镜像只换域名。

三条不可违反的规则（详见两个仓库的 README）：

1. **只增不删**。旧版本必须一直可取，否则 `wave install <包>@<旧版本>` 永久失效。
2. **同名不覆盖**。需要重建时换版本后缀，例如 `1.8.2-1`。
3. **字节原样搬运**。校验值因此与上游一致，可直接用官方 SHA256。

于是 4.0 的行为是：没有 `file` 就报错并说明是数据缺陷，**不会悄悄回落到 `url`**。
静默回落等于把「别人的服务器挂了就装不上」这个问题又带了回来，而且没人察觉。
把老记录补上 `file` 是数据侧的一次性迁移，用 `scripts/backfill_file_field.py` 生成。

### 5.3 索引自动化

包索引仓库有一套自动更新流水线，目标是「让索引跟上上游，但不让机器人直接改主分支」。

它每天定时运行一次，也可手动触发。处理范围被刻意收得很窄：只处理下载地址指向公开 GitHub 发布页、版本号是纯数字、且当前记录没有依赖声明的包。依赖需要人判断，所以带依赖的记录一律跳过。

匹配产物时要求三个条件同时成立且唯一：产物名里明确标出目标架构、明确标出 macOS、并且把版本号与架构词替换成占位符之后，与现有记录的文件名形状完全一致。这一条是整套逻辑里最有价值的防护 —— 它自动排除了校验和文件、通用二进制、带额外后缀的变体。只要候选不唯一，就跳过而不是猜。

校验值优先取上游发布页提供的摘要；上游没提供才下载计算，且有体积上限与主机白名单。

所有结果写到一个专用分支，开一个待审 PR 并指派维护者。维护者合并、且 PR 正文含一个隐藏标记时，才在程序仓库创建一个索引更新发布，并显式标记为非最新 —— 避免索引更新抢走「最新发布」这个位置，那个位置应当属于应用版本。

跳过而不是猜测的清单值得记住：conda 包、自定义镜像、带依赖的记录、歧义或通用产物、非数字版本标签、以及测试用包。

## 六、命令参考

入口命令下挂十三个动作：安装、升级、卸载、列出已装、远程搜索、详情、自更新、建立无版本链接、删除无版本链接、查询无版本链接、查看版本、查看更新、查看地址来源。

| 命令 | 作用 |
| --- | --- |
| 安装 | 装包；默认取远程最高版本，也可指定版本 |
| 升级 | 把包带到远程索引里的最新版本；可顺带清理旧版本 |
| 卸载 | 卸载指定版本；不带版本号时按最高版本处理 |
| 列出 | 扫描已安装包目录 |
| 搜索 | 在远程索引里按名字匹配 |
| 详情 | 本地已装版本、远程可装版本、以及元数据说明 |
| 自更新 | 更新 MacWave 自身 |
| 建立链接 | 把不带版本号的链接指向最高已装版本 |
| 删除链接 | 移除该链接 |
| 查询链接 | 显示该链接当前指向哪个版本 |
| 查看版本 | 打印当前生效的 MacWave 版本号 |
| 查看更新 | 只报告哪些已装包有新版，不下载任何东西 |
| 查看地址来源 | 打印每类数据实际取自哪个地址，标明来自环境变量还是内置默认值 |

旗标分为三类。通用输出类包括帮助、版本、详细日志。网络类包括断点续传、代理、跳过证书校验、限速。安装控制类包括指定版本、安装或卸载时不碰无版本链接、以及对所有已装包批量执行链接操作。

版本可以用两种等价方式指定：附着在包名后面，或通过版本旗标传入。两者都不给时，才去远程索引取最高版本。

卸载与链接的关系值得单独说明。卸载某版本后，无版本链接会自动降级到次高版本；一个版本都不剩时链接被删除。若显式要求保留链接，但保留会导致链接指向正在被删除的版本，命令会拒绝执行 —— 宁可不做，也不留下悬空链接。

升级之所以单独成为一个动作，是因为版本是共存的：安装一个新版本不会动旧的。所以「升级」= 装上最新版本 + 按需清理旧版本，后者由移除旧版本旗标触发。

那个旗标有四种写法，完全等价。长参数给了三个，是因为单复数记不牢 —— 有人记 `--remove-old-version`，有人记 `--remove-old-versions`，与其让其中一半人报错，不如都收，再给一个短到不用记的 `--rov`。短参数刻意选了 `-X`：`R` 与 `r` 要留给递归、反转、回滚这类将来的语义，`X` 没有别的含义，而且形状像「删除」的叉。它既认单独出现的 `-X`，也认混在短旗标簇里的 `-Xv`（等于 `-X -v`），与 `-abc` 拆成 `-a -b -c` 的既有规则一致。

清理策略分三档：只有一个旧版本就直接移除；有多个时先问「全部移除」，答否再像卸载那样列出来让用户挑；非交互环境读不到答复时一个都不删 —— 删错了就丢数据，而少删一次只是留下些占空间的东西。顺序上刻意先装新版本再清理：安装失败时旧版本还在，用户手上始终有一个能用的版本。若远程索引反而落后于本机已装的版本，命令只提示、不下载也不删除，避免把降级说成升级。

## 七、核心机制

### 7.1 安装流水线

一次带依赖的安装，按顺序经历这些阶段：入口读取配置并把几个代码目录注入模块搜索路径；安装编排解析参数与架构；确定版本（显式指定优先，否则远程取最高）；取元数据拿到可执行文件名；取版本记录拿到地址、校验值与依赖列表；下载；把安装参数与依赖列表交给安装核心装本体；递归安装全部依赖；最后做动态库路径重写；再建立无版本链接。

有三个顺序是刻意的，而且每一个都对应过真实故障。

**依赖标记要早写。** 路径重写要靠它知道该去哪些依赖里找库，它同时也是卸载时清理依赖的唯一依据。

**路径重写必须最后统一做。** 依赖声明顺序与实际库依赖顺序未必一致 —— 完全可能出现「先声明的库反过来依赖后声明的库」。如果装一个就立刻改一次，先改的那个会因为目标库还没落盘而改不动，之后也不会被补上。所以必须等全部产物就位，再一次性扫描全部产物。

**反向标记最后打。** 只有依赖真正装好了才记录「谁依赖了我」，避免中途失败留下错误标记，导致日后的级联卸载判断出错。

### 7.2 两种安装形态

同一套安装核心被两种形态复用。

**软件包形态**面向最终用户：解压后只取一个可执行文件。优先找与包同名的；找不到才取第一个，并给出警告。这个兜底策略让命名不规范的上游也能装上，但会提示你结果可能不是你想要的。

**依赖形态**面向库：保留整棵解压目录。库包不能只取一个文件，头文件、动态库、资源目录都可能是运行时需要的。安装后把其中可执行目录下的每个文件都建一条链接，因此不依赖「与包同名的可执行文件」这个假设 —— 一个依赖往往提供很多个命令。

两种形态都遵循同一套收尾动作：校验、解压、复位可执行权限、建链接、写依赖清单。

### 7.3 依赖模型

依赖关系用三类记录表达。

产物目录里有一个文件记录「我依赖谁」，一行一个带版本的引用。

依赖目录里可能有两种反向标记：一种表示我被某个软件包依赖，另一种表示我被某个依赖依赖。

卸载时的算法是：先删掉自己写下的依赖清单，再逐一检查每个被依赖者的反向标记。只有当一个依赖身上再没有任何标记时，才把它连同它自己的依赖一起级联删除。共享依赖因此不会被误删 —— 它身上还有其他使用者留下的标记。

### 7.4 动态库重定位与重签名

这是 MacWave 最关键、也最容易被忽视的机制，几乎所有「装好了但一运行就崩」的问题都指向它。

**问题本身。** 从 conda 或上游直接拿到的库，其内部记录的动态库引用通常是一个相对路径标记。而这类库自带的搜索路径只包含「与自身同目录」，一旦被放进多层嵌套的依赖树里，跨目录引用必然解析失败。运行时表现为：找不到某个动态库。

**解决方法。** 安装结束后，对所有产物做一遍扫描：读出每个二进制与库的动态库引用；建立一个「库文件名 → 本地实际路径」的索引，查找顺序是产物自身的库目录、它依赖清单里列出的依赖、最后是其余已安装依赖兜底；把能解析的引用改写成安装根目录下的绝对路径；对于库本身还带自身标识的，一并改写。

**为什么必须重签名。** 修改二进制会让原有签名失效。Apple 芯片上失效签名的可执行文件会被系统直接拒绝运行，所以每次改写后都要重新做一次 ad-hoc 签名。

**只改该改的。** 系统目录下的库一概不动，避免把系统组件卷进来。

**幂等性是刻意保留的。** 已经正确的引用会被直接跳过，因此这个流程可以安全地重复执行，也就成了修复既有安装的标准手段。

### 7.5 软链接模型

每个已安装版本都有一个带版本号的链接，永远可用。另有一个不带版本号的链接，指向「当前默认版本」。安装时默认会建立后者，可用旗标关闭。

这个双层结构带来两个好处：脚本里写带版本号的名字，永远精确可控；交互使用时写不带版本号的名字，跟随默认版本。默认版本由链接命令族管理，可以查询、切换、批量处理。

### 7.6 解压

支持八种常规归档格式加一种特殊格式。常规格式按扩展名分派给系统工具；裸的 xz 例外，因为 macOS 不自带对应命令，改用 Python 标准库解。

特殊格式是 conda 的第二种包格式。它本质上是一个 zip，里面装两个用 zstd 压缩的 tar：一个放元数据，一个放真正的载荷。安装只取载荷那一个。解压时保留符号链接（conda 包大量使用），同时挡掉危险路径。这条路径需要较新的 Python，旧解释器会明确报错而不是静默出错。

### 7.7 版本号解析

版本比较不是简单的字符串排序，需要处理语义化版本的各段数值比较、预发布阶段的先后、以及若干社区特有的后缀标记。此外还约定「两段版本与三段版本等价」，因此 2.3 与 2.3.0 视为同一版本。依赖版本比较复用同一套逻辑，避免两处规则漂移。

### 7.8 网络行为

所有请求有超时上限，默认值由请求类型决定（元数据 30 秒、文件清单与单个文件 60 秒、便携解释器归档 900 秒）。`--max-time` 可以把它们统一改成别的值，写法是 curl 风格的一段时间（`40s`、`1min20s`、`2h`，无单位按秒），但内部一律折算成整数秒使用。下载超时或连接失败会询问是否重试，而不是直接失败。下载过程写临时后缀文件，因此可以断点续传。代理与限速都可在命令行指定。自更新那条路径不看是否有终端，直接按次数重试，详见 8.1。

实践中限速反而能提高稳定性 —— 不稳的网络下，全速下载更容易触发超时重试循环。

## 八、自更新与版本迁移

### 8.1 两层结构

自更新分成两层，这个划分本身就是设计要点。

第一层是命令入口：取回最新版本信息，与当前生效的版本文件比较，只比较数字段，因此 2.3 与 2.3.0 视为相同。已是最新就直接返回；否则提取更新命令并执行，同时把目标版本与目标分支作为环境变量传下去。

第二层是更新脚本：定位配置目录与安装根目录，取回文件清单，逐个下载并复许可执行权限，清理字节码缓存，重写版本文件。

**为什么脚本要自带解析能力。** 更新脚本不能把「解析清单」这件事交给一个独立的新文件，因为那个新文件本身还没被下载下来。这是一个典型的先有鸡还是先有蛋问题，解决办法就是让解析逻辑内联在脚本里。

**为什么更新完要复核。** 用命令替换方式执行远程脚本时，远程拉取失败并不会让外层命令返回失败，看起来像成功。所以更新完成后必须回读版本文件确认版本真的变了，否则报错。这个复核救过很多次「静默失败」。

**超时与重试。** 第二层给每个请求都设了超时：没有超时的话，一次「连上了但不再有数据」的抖动会让自更新无限挂住，用户看到的只是一个不动的界面。失败会按 curl 的退出码决定要不要重试：超时、连接重置、传输中断这类重试三次；404 与写盘失败直接放弃，因为重试它们只是白等。下载一律先写 `<目标>.macwave-part`，成功后再 `mv` 到目标位置，所以重试期间安装树里不会出现半个文件，全部失败时原地那份好文件也不受影响。放弃时打印出是哪个文件没下成；因为版本文件写在全部文件到位之后，此时版本号仍是旧的，网络恢复后再跑一次即可继续。

**`--max-time` 怎么传。** 命令行怎么写就怎么往下传：入口层不解析时长，`selfupdate.py` 用它约束自己的请求后，把**原始文本**经环境变量交给第二层，由第二层再解析一次。这样只有一套规则，两层不会各自算出不同的超时。第二层用 `awk` 把 `40s` / `1min20s` / `2h` 这类写法折算成整数秒再交给 curl —— curl 的 `--max-time` 只收纯数字，直接传 `1min` 会被它拒绝。

### 8.2 跨大版本守卫

更新脚本开头有一道守卫：目标版本与当前版本的大版本号不同时，直接拒绝并提示改用安装器。

理由是跨大版本通常同时改代码结构与目录结构，逐文件替换无法保证一致性，而安装器有完整的目录创建与迁移流程。

守卫写在发布分支的更新脚本里，因此随每个新版本自动下发，不需要在数据仓库里逐版本登记规则。反过来，同一大版本内的补丁升级可以正常自更新。

### 8.3 迁移机制（3.x 与 4.0 不同）

4.0 起，目录结构变更的迁移**写在 `macwavedata/<版本>/update_commands.sh` 里**，
与「下载哪些文件」用同一份脚本、同一次执行。

3.x 用的是另一套：`updatedata/<版本>/dir_structure_change` 单字符标记 +
`transfer_commands` 迁移脚本，安装与自更新都要先检查标记、再决定跑不跑。这套机制在 4.0
被合并进更新脚本，因为两者本来就该原子地一起完成 —— 文件按新结构落盘、旧位置清理掉，
分两步做就会出现「标记说改了但脚本拉不到」那种半迁移状态。

更新脚本通过环境变量获知上下文（`MACWAVE_INSTALL_DIR`、`MACWAVE_CONFIG_DIR`、
`MACWAVE_CURRENT_VERSION` 等，完整清单见 [DATA-LAYER.md](DATA-LAYER.md)），自行判断要不要
动作。这比在脚本里写死判断条件灵活，也让同一份脚本能安全地在多个补丁版本目录下重复执行。

### 8.4 主分支与发布分支的镜像

发布分支由版本数据声明，不由代码写死。镜像工作流在两边的任一侧有新提交时，把另一侧快进过去。只做快进，绝不覆盖；两边都已经分叉时直接报错，交给人工处理。

推送使用的凭据必须能绕过分支保护规则 —— 机器人身份无法进入规则集的豁免名单，所以用了一个属于组织管理员的令牌。令牌推送会再次触发同一个工作流，但那次运行会发现两侧已经相等而直接退出，不会形成循环。

### 8.5 每个地址都能换掉（4.0 起）

4.0 把「从哪儿取东西」变成一组环境变量。镜像站因此是**配置**而不是命令 ——
把变量写进 shell 配置或 CI 即可。4.1 起有 `wave mirror`，但它只**报告**每类数据
实际取的地址（标明来自环境变量还是内置默认值），不负责改。

| 变量 | 取什么 | 默认（不设时） |
| --- | --- | --- |
| `MACWAVE_API_DOMAIN` | 包索引与依赖索引的元数据 | `infosource` 的 raw 地址 |
| `MACWAVE_BOTTLE_DOMAIN` | 预编译软件包 | 无（未设即报错） |
| `MACWAVE_DEPS_DOMAIN` | 依赖库 | 无（未设即报错） |
| `MACWAVE_CORE_DOMAIN` | MacWave 自身文件 | `MacWave` 的 raw 地址 |
| `MACWAVE_PYTHON_DOMAIN` | 自带 CPython | `Python` 仓库的 raw 地址 |
| `MACWAVE_SELFUPDATE_DOMAIN` | 自更新数据 | `Selfupdate` 仓库的 raw 地址 |
| `MACWAVE_PKG_SOURCECODE_DOMAIN` | 软件包源码 | 无（预留，暂未使用） |

三个要点：

- **默认值仍是 3.x 的地址**，所以一个都不设时行为完全不变。这条有断言盯着
  （`scripts/domains_test.sh` 逐字比对 11 个拼出来的地址）。
- **Bottle / Deps 没有回落**。缺域名就停下并说明怎么设，不会悄悄回到上游 ——
  那等于把 4.0 要解决的三个问题又带回来，而且没人察觉。

  默认值指向 GitHub Releases 而不是仓库文件：git 有 100 MiB 单文件硬限，而已有
  172.9 MB 的产物；Releases 单文件上限 2 GiB，且不限制总量与带宽。它的下载路径
  `/<tag>/<资产>` 与静态镜像的 `/<包名>/<文件名>` 同形，所以国内镜像只要 `rsync`
  出同一棵树，不需要理解任何协议。
- **版本清单是唯一不能简单镜像的东西**：它走 `api.github.com`，与索引不是一台机器。
  设了 `MACWAVE_API_DOMAIN` 时改读镜像自己的 `<路径>/versions`（一行一个名字），
  没设时仍用 GitHub API。

配置校验在拼地址之前完成：非 https（本机回环除外）、带空白或引号的值一律拒绝，
因为它们会进 URL、也会进错误信息。值末尾的斜杠会被去掉，所以镜像地址写不写 `/` 都行。

Python 与 shell 各有一份实现（`lib/domains.py` 与两份脚本里的 `mw_domain` 块，
后者是 `curl | bash` 执行、没有本地文件可 source）。三处的默认值由
`scripts/check_domain_defaults.py` 比对，漂移会让 shell 下的地址和 Python 下的不一致。

## 九、日常维护

### 9.1 加一个包

需要为两种架构各准备两份记录：一份元数据，一份版本记录。

元数据写清楚说明、主页、许可证、作者与可执行文件名。版本记录写下载地址、校验值，需要依赖时再追加依赖声明。

若上游是 GitHub 发布页且版本号规范，通常可以让索引自动化生成版本记录，人工只需补元数据。若上游是 conda 或自定义镜像，则需要手工填写。

填完之后必须做两件事：跑一遍数据审计，确认字段完整、引用可解析、元数据与版本记录都存在；再在本地用校验工具逐条检查新记录。最后实际安装并运行一次 —— 静态检查通过不代表运行时能加载。

### 9.2 加一个依赖

依赖记录放进依赖索引，结构是架构、依赖名、以及元数据与版本记录。元数据里记录的是依赖名而非可执行文件名。

几条实践要点：依赖必须按「保留整棵树」的形态安装；装完一定要真的运行一次程序，确认没有动态库加载失败；改动了依赖关系后要跑依赖链测试，而不是只测单个包。

依赖树上还有一个容易忽略的点：同一个库可能同时被软件包和另一个依赖引用。此时它身上会有多条反向标记，任何一条都不能被误删，否则级联卸载会提前把它带走。

### 9.3 新增程序文件

只需要在版本数据的文件清单里加一行。不要修改安装器或更新脚本 —— 它们读的是同一份清单，这正是把清单外置的目的。

### 9.4 开新版本分支

发布分支由版本数据决定，所以开新分支的步骤是固定的：把版本数据里的发布分支字段改成新分支名，同时更新版本号、发布日期与构建号；把新分支名加进持续集成的工作流触发列表；更新项目说明里的当前分支描述；正式发布时更新两份说明文档里的最新版本号；以及更新官网页面上的版本行。

镜像工作流不用改，它只认版本数据里的那一个发布分支。历史分支也不会被误动。

### 9.5 测试与审计工具

仓库里有一组脚本，各自负责一类回归：随机包端到端、依赖链、无版本链接、压缩格式、自更新、隔离环境、配置目录解析。

数据审计工具支持两种模式：一种检查数据本身的完整性（字段、引用、元数据是否存在）；另一种把已安装依赖的实际动态库引用与数据声明对比，找出漏声明的依赖边。后者是排查运行时崩溃的利器。

还有一个很重要的环境变量：给它一个目录，整条链路就会把该目录当作根，所有系统路径与家目录都挂到它底下。做危险实验、复现历史版本、测试迁移脚本时都应该用它，确保不碰真实系统。

## 十、故障排查

### 10.0 一分钟定位

| 症状 | 去这里 |
| --- | --- |
| 命令找不到 | 10.1 |
| 升级后还是旧版本、配置不生效 | 10.1 |
| 下载超时、卡住、校验失败 | 10.2 |
| 运行时报找不到动态库 | 10.3 |
| 程序崩溃或功能缺失 | 10.3 |
| 解压失败 | 10.3 |
| 链接指向不对、卸载被拒 | 10.4 |
| 提示不能跨大版本更新 | 10.5 |
| 提示更新未完成但其实成功了 | 10.5 |
| 老版本取不到数据 | 10.6 |
| 自动化 PR 或发布没出现 | 10.6 |
| 推送被拒绝 | 10.7 |

### 10.1 安装相关

**命令找不到。** 先确认配置目录里记录的安装根目录是哪一个 —— 两处配置都要看，因为系统级优先。然后确认 PATH 里是否包含三个该包含的目录。常见原因是 shell 配置写进了与你当前所用 shell 不匹配的文件，或者改了配置但没重新加载。临时验证可以手工导出 PATH 后在当前会话里试。

**用户级安装却读到了旧版本或旧配置。** 这是 2.5 之前最经典的坑。系统级配置存在时永远优先，所以残留的旧系统级配置会盖住新的用户级配置。先列出两处配置目录看谁在那里、修改时间是什么时候；若是废弃的旧配置，备份后移走，再重跑安装器。

**安装中途失败。** 安装器刻意不自动清理。按报错修好网络、权限或磁盘后直接重跑；安装是幂等的，已下载内容会被复用。

**权限错误。** 系统级目录需要提权，用户级目录不需要。若用户级仍报错，检查目录属主是否被之前的提权操作改成了别人。

### 10.2 下载与校验

**下载超时或卡住。** 请求有超时上限。网络不稳时优先指定代理，其次考虑限速 —— 全速下载在不稳的链路上更容易反复触发超时。中断后用续传参数重新执行。

**校验值不匹配。** 含义是拿到的文件与索引记录不一致。三种可能：上游替换了同名资源（最常见）、索引记录写错、或者中间层缓存了旧文件。处理方式是拿上游发布页的摘要与记录比对，据此决定是更新索引还是新增版本记录 —— 不要用「跳过校验」来绕过，那会把问题推到运行时。

**跳过证书校验很慢。** 这是已知问题：跳过校验并不会跳过握手流程，反而更慢。优先修证书链或用代理，不要用它。

### 10.3 运行时

**找不到动态库。** 说明路径重写没生效，或重写时目标库还不在位。先确认依赖确实装了，再重装该包 —— 重装会重跑完整的路径重写。也可以手动对某个目录执行重写脚本，它是幂等的，安全。参数是目标目录与安装根目录。

**库文件明明存在却仍报找不到。** 多半是引用指向了另一个路径：旧安装、被覆盖的同名库、或者从另一个前缀迁移过来的产物。重装是标准解法。

**程序能跑但功能异常或崩溃。** 通常是依赖版本不匹配 —— 典型的例子是某个命令需要新版本库里才有的符号，而索引里声明的是旧版本。用审计工具的边比对模式查漏声明的依赖。

**解压失败。** conda 格式需要较新的 Python；裸 xz 依赖 Python 标准库；其余格式依赖系统命令是否存在。

### 10.4 卸载与链接

**无版本链接指向不对。** 链接会自动跟随最高已装版本，但要显式触发。先查询当前指向，再重新建立链接。

**保留链接的卸载被拒绝。** 这是设计行为：保留会导致链接悬空指向正在删除的版本。要么先删除链接，要么不要要求保留。

**卸载后残留目录。** 通常来自中途失败的安装，依赖清单或反向标记没写全。手动删除对应版本目录即可；但若该依赖身上还有别人的标记，就不能删。

### 10.5 自更新

**提示不能跨大版本。** 用安装器重装。这不是故障，是防呆。

**提示更新未完成但实际已更新。** 2.5 之前的自更新把版本文件路径写死，配置被迁移后复核读不到文件。确认版本文件内容已经是新版本即可；之后升级请用安装器。

**更新后命令消失。** 检查文件清单是否漏列了新文件，以及版本文件是否写到了正确位置。

### 10.6 数据与索引

**老客户端取不到数据。** 旧数据分支已改名为遗留前缀。升级到 3.0 以上，用安装器。

**自动化 PR 没出现。** 依次检查三件事：索引仓库里是否存在那两个令牌、自动化令牌的属主是否在分支保护的豁免名单里、以及运行日志里的跳过原因。

**合并了却没有发布。** 检查 PR 正文是否带隐藏标记、来源分支是否为约定的自动化分支、以及是否来自同一仓库而非派生仓库。

**镜像工作流失败。** 检查镜像令牌是否存在且属主为组织管理员。另外，主分支与发布分支分叉时工作流会故意报错，需要人工合并 —— 这是设计如此。

### 10.7 开发与提交

**推送被拒绝。** 所有分支受规则集保护：必须走 PR 且需批准。管理员可豁免，普通协作者不行。

**持续集成在预发布解释器上假绿。** 出现过「检查没真正执行却通过」的情况。流程里有断言校验实际版本号，怀疑假绿时看日志里那段断言输出。

**误提交了缓存或系统文件。** 已在忽略清单里；若历史提交带入，从索引移除即可，不必删除工作区文件。

| 依赖安装 | 解析依赖数据、递归安装、打标记 |
| 依赖查询 | 判断依赖是否已装 |
| 路径重写 | 改写动态库引用并重签名 |
| 脚本目录 | 各类回归与数据审计 |
| 文档目录 | 本文件与持续集成记录 |

### 11.2 术语

| 术语 | 含义 |
| --- | --- |
| 安装根目录 | 整棵安装树的顶层 |
| 元数据记录 | 描述包本身的记录，无下载地址与校验值 |
| 版本记录 | 描述某个具体版本的记录 |
| 依赖清单 | 产物目录里记录「我依赖谁」的文件 |
| 反向标记 | 依赖目录里记录「谁依赖我」的文件 |
| 软件包形态 | 只取一个可执行文件的安装方式 |
| 依赖形态 | 保留整棵目录树的安装方式 |
| 发布分支 | 版本数据声明的分支，与主分支镜像 |
| 索引更新发布 | 为索引变更创建的发布，显式不标记为最新 |
| 自带解释器 | MacWave 自己分发的那份 CPython（`python/<版本>/`），默认用它运行 |
| 私有环境 | 用自带解释器创建的 venv，三个依赖装在里面 |

### 11.3 版本行为对照

| 想做的事 | 2.x 及更早 | 3.x |
| --- | --- | --- |
| 找包索引 | 程序仓库的旧数据分支 | 独立索引仓库 |
| 找版本数据 | 程序仓库的旧数据分支 | 独立版本数据仓库 |
| 升级大版本 | 安装器 | 安装器 |
| 升级小版本 | 自更新 | 自更新 |
| 新增程序文件 | 改安装与更新脚本 | 只改文件清单 |
| 配置位置 | 一律系统级 | 跟随安装级别 |

### 11.4 出问题时按序自检

先确认配置目录里记录的安装根目录是哪一个（两处都看）。再确认当前版本号与 PATH 是否包含三个该包含的目录。然后列出已安装包，确认包真的在。接着验证索引数据源可达。最后跑一次数据审计，确认依赖声明完整。

这五步能覆盖绝大多数「装完不好用」的情形，并且每一步的结论都会把问题范围缩小一半。
