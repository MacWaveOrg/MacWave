# 各版本为什么要更新

这份文档回答一个问题：**我手上的 MacWave 该不该升，升了会得到什么。**

按版本倒序排列，最新的在最前。每版给出三样东西：**为什么要升**（不升会怎样）、
**更新了什么**（具体改了哪些行为）、**规模**（代码量变化，用来判断这次改动的分量）。

> 想看「这软件是怎么长出来的」去看 [MacWave 发展历史](../history/zh-Hans/MacWave发展历史.md)，
> 那份是叙事；本文只讲升级决策。
>
> 2.1 及更早属于早期形态，与现代版本不构成升级路径，本文只在最后一张表里带过。

---

## 快速判断：你该升到哪一版

| 你的情况 | 建议 | 原因 |
| --- | --- | --- |
| 已经装在 4.x | **升到 4.1.3** | `wave selfupdate` 一条命令，无迁移 |
| 装在 3.2.x | 先升 4.0.0，再到 4.1.3 | **跨大版本不能自更新**，4.0 需从官网重装 |
| 装在 3.0.x / 3.1.x | 同上 | 3.0 起是独立数据仓库，路径已稳定，但仍受跨大版本限制 |
| 装在 2.6.x 及更早 | **从官网重装** | 3.0 起数据结构变了，2.x 拿不到新数据 |
| 从没装过 | 直接装 4.1.3 | 官网一条命令 |

**跨大版本为什么不能自更新**：每个大版本都会同时改代码结构与目录结构，局部替换文件
无法保证一致性。这条守卫写在各版本的自更新脚本里，所以旧版会自己拦下来并指向官网。

## 4.1.3（2026-10-30）

**为什么要升。** 4.1.1 的自更新会**报告成功，但并没有装全**。终端里刷过一串 404，
最后照样打印「已更新到 4.1.1」。已经升过 4.1.1 的机器本身是好的（漏掉的只是两个
`__pycache__` 目录，Python 会自己重建），但这个机制本身很危险：同样的静默会发生在
任何一个真正需要的文件上。4.1.3 让它要么装全、要么明确失败。

**更新了什么。**

- 升级清单不再包含 `pkg/__pycache__`、`surfboard/__pycache__`，也不再包含
  `lib/install.sh` 与 `lib/uninstall.sh`。来源是发版命令里的 shell 通配符
  （`pkg/*` 会匹配到目录），而过滤器只写在另一条入口上。
- 任何一个文件下不到、没能就位、或加不上可执行位，**整次更新失败**，不写
  `VERSION.json` —— 于是重跑 `wave selfupdate` 会从头再来一遍，能自愈。
- 「变更清单为空」在生成阶段就被拒绝。一条 `want` 都没有的升级脚本会瞬间「成功」
  返回，等于什么都没换，连报错都没有。
- 报错里的镜像地址打码（`https://用户:***@mirror/...`）。上一版会把它原样打印，
  等于把密码写进终端滚屏和求助截图。

**规模。** 代码基本没动（三处 `return` 改成 `exit`，加一个 `sanitize()` 与
`redact_url`）；新增一份 30 条的回归脚本 `update_commands_test.sh` 并进 CI。

## 4.1.1（2026-10-30）

**为什么要升。** 4.1.0 把镜像地址做成可配置的，但配好之后你没法确认「这次到底走了
镜像还是官方地址」——只能挨个 `echo` 环境变量，而其中几个带密码，不方便随手打印。
4.1.1 补上这个缺口。

另外三个小毛病：`wave update`（很多人这么拼）只会回一句「未知命令」加整篇帮助；
包名拼错时永远给同样的三行提示；想知道「有哪些包过期了」只能真的跑一次 `upgrade`。

**更新了什么。**

| 新增 | 说明 |
| --- | --- |
| `wave latest <包名>` | 只报告有没有新版，不下载任何东西。比较基准是**已安装的最高版本**，不是那个不带版本号的链接 |
| `wave latest --all` | 一次列出全部已安装包，末尾给「3 个里有 1 个可升级」的汇总 |
| `wave info --json` / `--yaml` / `--toml` | 同一组字段的三种机器可读格式，三者互斥 |
| `wave info --raw` | 把索引里的 `@common` 记录**原样**打印，连 `sha256` 和 `url` 一起。回答的是「这个作者名是从哪儿来的」 |
| 命令名拼错时给建议 | `wave update` → 提示 `upgrade`，并**保留其余命令行**，可直接粘回去重跑 |

**规模。** 代码 8079 → 8717 行（+638），py/sh 文件 26 → 27，29 个文件改动，
新增 3498 行、删除 36 行。新增的 `lib/latest.py` 是主力。

**怎么升。** `wave selfupdate`。无迁移步骤，不改数据格式。

## 4.1.0（2026-10-29）

**为什么要升。** 4.0 起所有远端地址都可以用环境变量替换，但替换之后
「到底生效了没有」只能靠逐个 `echo` 推断。设了变量不等于生效——拼错名字、
没重载 shell 都会静默失败，表现是「还是慢」，很容易误判成网络问题。

还有个实际问题：排查时最自然的动作是 `echo $MACWAVE_API_DOMAIN`，而它的值里有密码，
往往就留在群聊记录里了。

**更新了什么。** 新增 `wave mirror`：一条命令列出每一类数据**实际**从哪个地址取，
并标明该地址来自环境变量还是内置默认值。密码一律打印固定 6 个星号，
与真实长度无关——否则星号个数会泄露密码长度。`--show-password` 才给真值，
`--hide-user` 连用户名一起盖掉。

**规模。** 代码 7791 → 8079 行（+288），7 个文件改动，+498 / −2。
新增 `lib/mirrorinfo.py`。

> 4.1.0 有个遗留问题：它没把 `configdata` 和 `Selfupdate` 两处版本指针推上去，
> 4.x 用户当时收不到更新提示。4.1.1 已一并修正。

## 4.0.0（2026-10-29）

**这是整个项目最大的一次改动**（+4747 / −827，34 个文件）。核心是**软件包的来源**变了。

**为什么要升。** 在此之前，每条包记录只保存一个指向上游的 URL，实际下载发生在
第三方服务器——从大陆访问 `github.com` 实测三次里两次连 TCP 都建不起来。
MacWave 的产物又偏大（pandoc 40 MB、ollama 172.9 MB），这种链路基本下不完。

4.0 改由 CI 预先取回上游产物、校验 SHA-256、再托管到我们自己的 Release，
客户端只从镜像取。国内下载从「可能失败」变成「20~50 ms」。

**更新了什么。**

| 变更 | 对使用者的意义 |
| --- | --- |
| 产物预取 + 自托管 | 国内下载速度从不可用变成 20~50 ms |
| `--proxy` 作用于全部请求 | 以前只影响下载包体那一步，取索引、取依赖元数据、自更新全都绕过它，内网用户会卡在「Cannot fetch @common file」 |
| 新增 `--install-from-source` | 直接从源码构建，不依赖预取产物 |
| 包名支持非 ASCII | 以前只认 ASCII，中文包名会被拒 |
| `-v` 逐步说明 | 失败时能直接看出停在哪一步、请求了哪个地址、服务器答了什么 |
| 帮助信息重新排版 | 按命令分组，不再是一大段 |

**注意：4.0 不支持用它自己之前的版本自更新过来。** 3.x 用户会看到跨大版本守卫的提示，
需从官网重装。装过一次 4.0 之后，4.x 内部就能正常 `wave selfupdate` 了。

**规模。** 代码 6833 → 7791 行（+958），py/sh 文件 23 → 25。

## 3.2.2（2026-10-28）

**为什么要升。** 两个都不致命但很烦的问题。

一是 `--proxy` 只覆盖下载包体那一步——取索引、取 `@common`、取依赖元数据全绕过它。
内网用户加了 `--proxy` 仍然卡在「Cannot fetch @common file」，一个字节都没下到。

二是安装器会误报「安装未完成」。它取不到某个预期文件时会触发 ERR trap，
于是明明成功的安装最后打出一段失败信息。

**更新了什么。** `--proxy` 现在覆盖整条命令（实现方式是把值写进
`HTTPS_PROXY` 等环境变量，`requests`、`urllib`、子脚本里的 `curl` 都读这套，
一处生效、全部覆盖）。安装器的 ERR trap 收窄到真正失败的分支。

**规模。** 6 个文件改动，+171 / −3。改动不大，但都是「以为能用其实不能用」的坑。

## 3.2.1（2026-10-27）

**为什么要升。** `--remove-old-version` 只能写成 `--remove-old-version`，太长了。
日常清理旧版本每次都要打 20 个字符。

**更新了什么。** 四种写法都收：`--remove-old-version`、`--rov`（短参数）、
以及 `wave remove-old` 一类旧拼写。短参数定为 `-X` 而不是别的字母，是为了不与
既有的 `-h`/`-V` 混淆。

**升级时可能看到一次停顿**：旧版脚本会联网确认自带解释器的版本声明，那段时间没有任何
输出，看上去像挂住了。**这不是卡死**，等它过去即可。

**规模。** 11 个文件改动，+485 / −68。

## 3.2.0（2026-10-24）

**为什么要升。** 升级一个包以前要两步：先 `install` 装新版，再自己找出哪个是旧版、
手动 `uninstall`。忘了第二步，旧版本就一直占着磁盘。

**更新了什么。**

```sh
wave upgrade jq                        # 装最新版，保留旧版
wave upgrade jq --remove-old-version   # 装完顺手清理旧版
wave upgrade jq --rov                  # 同上，简写
```

**规模。** 代码 6414 → 6677 行（+263），py/sh 文件 22 → 23（新增 `upgrader.py`），
11 个文件改动，+661 / −44。

## 3.1.0（2026-10-22）

**这是推荐全员升级的一次**，因为它解决一个结构性依赖。

**为什么要升。** 3.0.x 及更早，入口脚本首行指向 PATH 上的 `python3`，而依赖是由
**安装时那个** `pip3` 装进去的。两处解释器一旦不一致，所有命令都会以
「模块不可用」的形式失败。

这不是假设：Homebrew 把 `python3` 从 3.14 升到 3.15 之后，`wave linkquery jq`
就再也跑不起来了。你的 MacWave 会因为一次无关的 Homebrew 升级而整个坏掉。

**更新了什么。**

| 项 | 3.0.x 及更早 | 3.1.0 起 |
| --- | --- | --- |
| Python | 必须自己装 3.14+，且要与装依赖时的解释器一致 | **不需要装** |
| 磁盘占用 | — | +约 30 MB（自带 CPython 3.14.9）+ 一个虚拟环境 |
| 入口 | 直接指向 `python3` | sh 启动器，按「私有环境 → 自带解释器 → 安装时记录的 → PATH」逐层实测，选**真能 import 依赖**的那个 |

顺带加了 `--max-time`（`40s` / `1min20s` / `2h`，纯数字按秒），
给弱网环境一个可调的等待上限。

**规模。** 代码 5583 → 6414 行（+831），24 个文件改动，+1868 / −107。

## 3.0.5（2026-10-17）

**这是一次安全更新，所有 3.0.4 及更早的用户都该升。**

**为什么要升。** 3.0.4 及之前，如果索引记录里**没有 `sha256` 字段**，安装器只打一条
黄色警告，然后照常下载并安装：

```
🌊 Warning: No SHA256 provided, skipping verification.
🌊 Successfully installed ...
```

索引记录是整条信任链的起点。每条记录声明「这个 URL 对应的内容，其 SHA-256 是 X」，
安装时把下载到的字节与 X 比对，是**唯一**把「索引承诺的内容」与「实际落盘的内容」
绑在一起的动作。

HTTPS 只保护传输过程，它保护不了两件事：索引本身被改动、上游替换同名产物。
一旦缺了 X，这两种情况都无从发现——装进来什么就会被直接执行。

**更新了什么。** 缺 `sha256` 一律拒绝安装，不再是警告后继续。

**规模。** 15 个文件改动，+1488 / −33。

## 3.0.4（2026-10-12）

**为什么要升。** 3.0.3 起有用户反馈：**装一个包，光在 Mach-O 重定位这一步就要等 5 分钟**。
三个问题叠加，全部在重定位路径上。

**更新了什么。** 实测基准是 18 个依赖树、14400 个文件（贴近装 `jq` 的真实规模）：

| 阶段 | 耗时 |
| --- | --- |
| 改造前 | **6 分 04 秒** |
| 索引只建一次 + 去掉逐文件 fork | 31 秒 |
| Mach-O 检测移出逐文件循环 | **4.8 秒** |
| 同上，且树里放入真实 Mach-O 二进制 | 5.9 秒（走完整 `otool` + `install_name_tool` + 重签流程，确认加速没牺牲功能） |

**规模。** 4 个文件改动，+121 / −55。改动很小，效果是 **76×**。

## 3.0.3（2026-10-12）

**为什么要升。** 装完的二进制找不到库——某些依赖包的归档里只有 `lib/` 一个顶层目录
（例如 `libcxx`），安装时被误当成「包装目录」下沉了一层，`lib/` 这一层消失，
路径替换再也接不上。受影响最明显的是 **`btop`**（依赖 libcxx），
`@rpath/libc++.1.dylib` 一直没能重写。

还有四个小问题：`--skip-ssl` 在非交互环境（CI、脚本）下抛 `EOFError`；
安装输出被内部诊断刷屏（装个 `jq` 有 18 个依赖就刷 18+ 行）；
3.0.2 引入的路径校验过严，导致 `wave link` / `unlink` / `uninstall` 全部误判成「越界」；
Ctrl+C 会甩一段 Python 栈回溯。

**更新了什么。** 只有真正的包装目录才下沉；`--skip-ssl` 读不到答复就按「拒绝跳过校验」
处理（往安全方向倒）；路径校验区分「会被写进去的路径」（严格跟随软链接）与
「只是操作链接本身」（不跟随）；`KeyboardInterrupt` 被捕获。

**规模。** 19 个文件改动，+946 / −173。

## 3.0.2（2026-10-10）

**为什么要升。** `--ver` 写在帮助里却不可用——任何用法都返回
`Input contains illegal fields.`。同时 `--flag=value` 这个写法对长参数不生效，
`--limit-rate=300K`、`--proxy=...` 会被读成 `=300K`。

更重要的是这一版开始做**安全加固**，值得单独说：

| 加固 | 做法 |
| --- | --- |
| 名字与版本号白名单 | 包名、版本号、远端 `@common` 里的 `bin_name`、依赖引用，一律只允许 `[A-Za-z0-9][A-Za-z0-9._+-]*`。含 `/ \ % @ :`、空白、`..` 或以 `-`/`.` 开头全部拒绝 —— 在进入 URL 或文件路径**之前**就挡下 |
| 最终路径必须落在安装目录内 | 所有会被创建、改名、删除的路径先归一化，再校验是否位于 `BASE_DIR` 之内，防路径穿越与软链接逃逸 |
| shell 侧再兜一层 | `surfboard/depsmanager.sh` 独立复核目标路径，即使有调用方绕过 Python 校验也写不出去 |

**规模。** 14 个文件改动，+1723 / −50。

**更新了什么。** 新增 `--dir-option=<路径>`，可以省略安装时那个交互式目录菜单。
自动化脚本里不用再喂编号了。

## 3.0（2026-10-08）

**这是一次不兼容更新，必须用 `install.sh` 重装，不能 `wave selfupdate`。**

**为什么要升。** 3.0 的核心变化不是功能，而是**把数据从代码仓库剥离**：包与版本数据
从「代码仓库的分支」迁出到独立仓库，依赖数据目录由 `surfboard/` 改名为 `deps/`。

这让「发版」和「加包」彻底解耦——以前加一个包要往代码仓库的分支里提交，
现在只需要改数据仓库。同时补上一条硬性规则：**跨大版本不允许自更新**。

**旧版怎么办。** ≤ `2.6.1` 读的仍是旧地址。那些旧分支还在，但已冻结、不再更新——
老版本继续能用，只是拿不到 3.0 之后的内容。

**规模。** 16 个文件改动，+237 / −76。改动看起来不大，因为是纯结构迁移。

## 2.6.0（2026-10-07）

**功能没有任何变化，只为迁移。** 代码仓库从 `github.com/Sha0huaZhang/MacWave`
迁到 **`github.com/MacWaveOrg/MacWave`**，新版本里所有地址都直接指向新组织。

**为什么要为一个地址发版。** `wave selfupdate` 在「当前版本 ≥ 远端版本」时直接短路
退出。只改地址的话，老用户永远不会去取新地址。提版本号才能让 2.5.x 的用户
执行 `wave selfupdate` 时**真正触发一次更新**，一次性完成迁移。

**规模。** 12 个文件改动，+52 / −26。

## 2.5.2（2026-10-06）

**这一版修的是卸载器，其中一条会删掉系统文件，务必升级。**

**为什么要升。** 五个问题，第一个是严重事故：

| 问题 | 后果 |
| --- | --- |
| 按官方写法卸载会删掉 `/bin/bash` | 文档给的命令是 `/bin/bash -c "$(curl ...)"`，这种调用方式下 `$0` **不是脚本路径**而是解释器自身。而卸载器收尾有 `rm -f "$0"`。**用了 sudo 的话会删掉系统的 `/bin/bash`**，此后任何 `#!/bin/bash` 脚本都跑不起来 |
| 无终端时照样删 | 确认提示读的是 stdin，stdin 是 EOF（`< /dev/null`、CI）时答复为空，于是跳过取消、直接删除 |
| 拒绝许可后留下悬空 PATH | 安装树删了，`.zshrc` 里的 PATH 还在 |
| `-h`/`--help` 对子命令不成立 | `selfupdate --help` 会**真的开始自更新** |
| 中途失败只留一个裸 curl 退出码 | 看不出失败在哪一步 |

**更新了什么。** 只有 `$0` 确实是「含脚本标记的普通文件」时才自删；确认从终端设备读；

## 2.5.0（2026-10-05）

**这是一次结构性变更，也是理解今天配置行为的关键。**

**为什么要升。** 在此之前所有安装都把配置写在系统级位置，读取规则是「系统级优先、
找不到再回落用户级」。这导致一个隐蔽故障：**用户级安装 + 机器上残留旧的系统级配置**
→ 新写的用户级配置被旧配置永久遮蔽。程序看起来装好了，实际读的是一个早就该废弃的目录。

**更新了什么。** 配置位置改成跟随安装级别：系统级安装写系统级位置，用户级安装写用户
自己的目录。同时补一段迁移逻辑，把旧版遗留的系统级配置搬到用户级——连配置文件本身
一起搬，否则程序会认为「没装」。

> **如果你还在 2.5 之前，请用 `install.sh` 升级，不要用 `wave selfupdate`。**
> 2.5 之前的 `selfupdate` 把配置路径写死在 `/opt/macwave_config`，配置被搬走之后
> 它升级完成时的复核会读不到、**误报「更新没有完成」**（实际已经成功）。
> 2.5 及以后没有这个问题。

**规模。** 代码 4635 → 4710 行（+75），24 个文件改动，+463 / −208。

## 2.4.0（2026-09-28）

**为什么要升。** 装完一个包，调用它要写全版本号（`jq@1.7.1`），太啰嗦。

**更新了什么。** 引入不含版本号的软链接机制：

```sh
wave link jq        # 给已装的 jq 最高版本建一个不带版本号的链接
wave linkquery jq   # 看这个链接指向哪个版本
wave unlink jq      # 撤销链接
wave link -a        # 给所有已装包都建一遍
```

链接自动管理有五条规则（最高版本被卸载后改指剩余最高版、安装时自动重指、
某包不再有任何版本时撤销、手动 unlink 过的会记住、含版本号的名称始终可用）。

**规模。** 代码 4220 → 4481 行（+261），py/sh 文件 20 → 21，11 个文件改动，+712 / −38。

## 2.3.0（2026-09-27）

**为什么要升。** MacWave 自己不能更新自己，只能重装。

**更新了什么。**

| 新增 | 说明 |
| --- | --- |
| 支持 `.xz` 格式 | 上游越来越多用 xz |
| `wave selfupdate` | 自更新命令。**但这一版自己还不能用它**——2.2 里没有这个命令，你无法这样升到 2.3，得先装 2.3 才能用 |

自更新分成两层：一层判断有没有新版本并触发更新，另一层真正按清单拉取文件。
这个分离是为了解决先有鸡还是先有蛋——更新脚本不能依赖「还没下载下来的新文件」。

**规模。** 代码 3760 → 4220 行（+460），py/sh 文件 18 → 20，23 个文件改动，+938 / −67。

## 2.2.0（2026-09-22）

**这是 2.x 里最重要的一版，也是「现代 MacWave」的起点。**

**为什么要升。** 在此之前，带依赖的软件包没法用——依赖要自己装、自己配环境变量，
而且系统库一更新就可能全坏。

**更新了什么。**

| 能力 | 说明 |
| --- | --- |
| 依赖自动管理 | 引用计数 + 自动清理。装一个 `jq` 会自动带上它的 18 个依赖，不需要手动处理 |
| 包与依赖都支持多版本共存 | 两者都放在 MacWave 自己目录下，不受系统库更新影响 |
| 新增 `ffmpeg` 等带依赖的包 | 第一种真正需要整棵依赖树的包 |

级联卸载的逻辑是：只有当某个依赖不再被任何人标记时，才会连同它自己的依赖一起删除——
共享依赖不会因为卸载其中一个使用者而被误删。

**规模。** 代码 3760 行、18 个 py/sh 文件。这是本文档统计口径的起点。
